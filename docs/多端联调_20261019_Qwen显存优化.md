# 多端联调：Qwen3.5-9B 显存优化

发生日期：2026-10-19。目标是在保留模型能力和既有任务效果的前提下，降低本地推理服务显存占用。先启动原配置作当日资源对照，再验证候选配置；未改变正式实例的模型或执行路由，未下发真机动作。

## 1. 改动及适用范围

默认模型启动脚本仍是独立实验目录 `<WORKSPACE>/Qwen3.5-9B/launch_vllm.py`。

- 原配置通过 `gpu_memory_utilization=0.92` 自动推算 KV 缓存，当日约 23 GiB。
- 新配置显式设置 `kv_cache_memory_bytes=10737418240`，即 **10 GiB**。同时设置 `gpu_memory_utilization=0.70`；在此 vLLM 版本中，显式 KV 字节数覆盖按百分比自动分配的缓存，二者不是相加。
- 官方 BF16 权重、原生 KV 精度 `auto`、视觉编码器、thinking、MTP-1、262144 上下文、32768 输出预算、采样参数、原图处理、视频读取及单请求调度均保持不变。
- 未量化权重或 KV，未采用 CPU 卸载，未截断长输入，未缩小上下文来降低数字。

依据为当前安装的 vLLM 0.18.0 配置实现与[官方缓存参数说明](https://docs.vllm.ai/en/v0.18.0/api/vllm/config/cache/)。服务原本即 `max_num_seqs=1`；旧缓存估算可容纳约 2.53 条满长度请求，新缓存约 1.10 条，仍满足原单请求调度和原上下文长度。

## 2. 当日资源实测

硬件为本机 49140 MiB 显存 GPU。约每秒采样 NVIDIA 进程显存，并按 `qwen35-vllm.service` 控制组 PID 归属统计；这些是**采样峰值**，不保证捕获所有瞬时峰值。

| 相同或注明范围的负载 | 原配置 | 10 GiB 缓存配置 |
| --- | --- | --- |
| 空闲模型服务 | 42.40 GiB | 30.26 GiB |
| 同一 218867 tokens 长输入的模型进程峰值 | 43.75 GiB | 30.26 GiB |
| 本轮候选配置全部图像／视频 | 原配置未在当天重跑完整资源采样 | 30.96 GiB |
| 本轮候选配置大脑 HTTP 场景 | 原配置未在当天重跑完整资源采样 | 30.96 GiB |
| 长输入期间服务组 PSS 内存峰值 | 约 3.97 GiB | 约 3.72 GiB |

长输入配对比较减少约 **13.48 GiB／30.8%**。模型加载内容未减少，主要减少空闲缓存预留。PSS 与控制组 `memory.current` 分别保留；后者还包含文件缓存，不能把控制组缓存归属变化误当成模型算法内存大幅下降。

候选阶段还观测到**整卡最高 35.21 GiB**，高于按进程归属记录的模型峰值；该差额没有进一步归因，不把整卡所有占用都记到模型进程，也不将 30.96 GiB 宣称为所有输入下的硬性显存上限。

## 3. 效果与速度核对

图像及视频使用[10 月 16 日完整配置测评](多端联调_20261016_Qwen35本地视觉测评.md)的同一输入、相同种子和参数复测：48 次图像＋3 次视频，共 51 次。

- **51/51 最终回答逐字一致。**
- **51/51 thinking 内容逐字一致。**
- **51/51 token 用量一致。**
- 原严格评分 37/51，新严格评分仍为 37/51，无通过项退化；原来计数、空桌和格式错误仍保留，不通过改变标签或删除失败样本提升分数。

上述图像／视频输出对照使用保留的 10 月 16 日原始响应；当日原／新配置的资源与长输入对照则实际分别启动运行，二者不能混称为全部项目都在当天完成双份 A/B。

同一合成长输入在当日两种配置下均实际处理 **218867 输入 tokens**、生成 1103 tokens，三个口令检索正确，最终回答一致。请求计时约 164.94 秒和 139.99 秒；这是单轮对照，不能单凭此宣称稳定加速。

正式大脑 HTTP 复验：

| 场景 | 新配置结果 |
| --- | --- |
| 正常抓放 | 约 86.39 秒；两次派发、落点和释放状态核验通过，个人物品不变 |
| 抓取失败后继续 | 首次约 86.38 秒进入 recovery_required，只派发一次；清除注入故障并继续原任务后完成，保留原命令和重试 |
| 放偏但执行端报成功 | 约 139.81 秒；两次派发后仍被核验拦截，随后取消实验任务 |
| 两项视觉描述 | 均返回描述，文字与原完整配置一致；原有形状误判和机器人末端误报仍在，不能记作视觉语义正确 |

本轮改变的是模型服务缓存分配，不是 Connection 业务机制；没有为配置改动重复运行全部源码回归。原有 574＋27 项回归属于 10 月 16 日证据，本次新证据为真实模型输出对照、长输入和大脑仿真实跑。

## 5. 同日追加：24GB 显卡部署候选

针对用户进一步降低显存的要求，追加三个候选档，各回放同一组 **7 次图像＋3 次视频**。这些是选取的固定样本，不是再次完成全量 51 次评测。硬件仍为本机 48GB 显卡，**未在实体 24GB 显卡上复验**。

三个档均保留原始 BF16 权重、原生 KV 精度、视觉、thinking、MTP-1、32768 输出预算、图像／视频处理与采样参数；将总上下文容量从 262144 改为 **65536 tokens**，KV 缓存从 10 GiB 改为 **2.5 GiB**。总上下文包含输入与输出，原 218867 tokens 输入不适用于这个档，不能将它描述为保留全部长上下文能力。

| 候选档／证据目录 `card24_runs/` | 模型空闲 | 模型推理采样峰值 | 整卡采样峰值 | 严格内容及格式通过／内容通过 |
| --- | --- | --- | --- | --- |
| 2048 预填充批量，默认分配器；`20261019-135323` | 21.87 GiB | 23.69 GiB | 24.03 GiB | 4/10；6/10 |
| 2048 批量，可扩展显存段；`20261019-135944` | 21.36 GiB | 22.62 GiB | 22.96 GiB | 4/10；6/10 |
| **保留原 8192 批量，可扩展显存段**；`20261019-140856` | **21.50 GiB** | **22.75 GiB** | **24.25 GiB** | **5/10；6/10** |

同一组选定样本的原配置严格通过为 5/10、内容通过为 6/10。前两档存在视频格式退化及正确／错误项互换，不能只看总内容分数相同就称效果无变化。第三档逐项通过／失败判定均保持一致；8/10 最终回答逐字一致，另外两条仅 JSON 空格不同；7/10 thinking 内容逐字一致。10 次请求均正常结束，无输出截断。保留原有错误，不把请求成功当作语义正确。

可扩展显存段通过 `PYTORCH_ALLOC_CONF=expandable_segments:True` 启用，用于减少分配碎片，不改变权重或 KV 精度。第三档整卡峰值超出 24 GiB，模型进程峰值为 22.75 GiB；恢复默认服务后检查发现另外两个导航仿真进程各占 582 MiB。由于没有记录它们在整个测试过程中的逐进程轨迹，不把整卡峰值差额精确归因，但明确不能用模型进程数字保证 VLM 与其他 GPU 服务在 24GB 卡上共存。

最终保留第三档作为**可选实验配置**，默认服务已恢复原 262144 上下文、10 GiB KV。独立模型目录的同一启动脚本新增参数：

```bash
# 仅预览已测试的 64K 候选配置，不启动或停止服务
python /home/fq/workspace/Qwen3.5-9B/launch_vllm.py --profile card24 --dry-run
```

去掉 `--dry-run` 会启动该档服务，须在现有同端口服务结束后使用；不带 `--profile` 仍为原长上下文档。已检查两个档的 dry-run 参数分别与原生效配置、第三轮实测参数逐项一致；此处没有切换默认配置。启动前版本保存在 `launch_vllm_before_card24_20261019.py`。

证据位于上述三个目录的 `candidate-argv.json`、`resources.jsonl`、`resource-summary.json` 与逐请求响应；后两档另有 `candidate-env.json`。汇总为独立模型目录的 `card24-audit.json`，审计脚本为 `audit_card24.py`。本次未对 64K 档重跑大脑动作、上下文极限、并发或长时间稳定性测试，不能把第 3 节的长上下文／大脑证据直接转移到此候选档。

[vLLM 官方模型配方](https://github.com/vllm-project/recipes/blob/main/models/Qwen/Qwen3.5-9B.yaml)列出了 BF16、单张 24GB GPU 的部署选项，与本轮模型占用量级相符；具体输入、后端配置与其他进程仍决定能否稳定运行。当前结论是 **24GB 作为该 9B VLM 的部署目标合理，64K 档在本机所测负载下约占 22.75 GiB，但仍需实体 24GB 卡及真实业务负载验收**。
