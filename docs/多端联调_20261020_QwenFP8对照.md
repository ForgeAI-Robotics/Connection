# 多端联调：Qwen3.5-9B BF16／FP8 对照

发生日期：2026-10-20。用户要求实际尝试 FP8，确认显存、速度和识别效果。FP8 模型独立放置于 `<WORKSPACE>/Qwen3.5-9B-FP8`，保留原 BF16 模型和默认 Connection 路由。累计完成 **246 次视觉模型调用**，不包含下载探测或健康查询。

## 1. 来源、完整性与兼容处理

来源为 [RedHatAI/Qwen3.5-9B-FP8-dynamic](https://huggingface.co/RedHatAI/Qwen3.5-9B-FP8-dynamic)，固定 revision `790f0576d2d77dd5322aa0603a470bd9e3a3d1f6`。这是部分权重／激活量化，原始发布文件约 14.03GB，不是所有模块都降为 8 位。

直连下载失败后使用现有代理和镜像。镜像的 .gitattributes 与官方不同，因此小文件改为直接取官方固定版本并验证 Git blob hash；大文件以官方 LFS SHA256 为准。约 11GB 分段已下载后有部分请求失败。先抽查重建片段与发布文件逐字节一致，再复用已有分段、BF16 数据及发布者 scale 补齐缺失字节，最终**主权重、MTP 权重和 tokenizer 全部通过官方整文件 SHA256**。这不是将未经校验的本地量化模型冒充发布版本。

首次启动失败：本机 transformers 4.57.6 不认识发布者 tokenizer 配置中的 `TokenizersBackend` 类。未升级现有 BF16 运行环境，也未开启远程代码执行，而是建立独立 `model-vllm` 兼容视图：

- 权重仍指向完整校验过的原发布文件。
- 文本／图像处理配置使用与 BF16 测试完全相同的本地副本，放在 `processor-compatible/`，不修改原发布目录。
- 共同词表的 token ID、规范化后的 BPE merges、聊天模板一致；发布者另有 7 个音频相关 token，本轮不测试音频。
- 113 对主测试请求的输入 token 数全部相同。

张量审计：无原始张量缺失；333 个视觉张量及 15 个 MTP 张量逐字节一致；同 dtype 的 599 个未量化张量均一致。发布快照中有 128 个 BF16 张量变为 FP8，另有 48 个 F32 张量存为 BF16。因此不能把它描述成所有未量化张量都保持原始精度。实际量化配置为按通道权重 scale、逐 token 动态激活量化，以发布 config 为准。

## 2. 对照条件

- 同一张约 48GiB 显存的 RTX 4090、同一 vLLM 0.18.0 环境，两个服务同时驻留；请求交替调用两端，仅组内并发，不让两端同时推理来比较延迟。
- 两端均为 65536 上下文、4 条执行序列、MTP-1、eager 模式。**KV dtype 保持 auto／BF16，KV 池均为 2.5 GiB，没有混入 KV 量化收益。**
- 请求 temperature 0、top_p 0.95、presence_penalty 0、seed 42、输出预算 1024，关闭 thinking。图像字节和提示相同。
- 每次请求使用新的图片 UUID 和前缀 salt，绕过图片／前缀内容缓存；模型、内核和 schema 经过预热。首次准备耗时另列，不丢弃原始记录。
- 19 道带标签问题包含此前仿真／OCR 问题，以及用户桌面图的物品存在、白色充电器数量、不可见内容判断。存在重复场景，仅一张主要实拍照片，不是 19 个独立机场场景。
- 主测 226 次：两端各 113 次，含预热、57 次约束输出标注题、19 次无约束标注题、原图开放描述、4MP 清单和三路并发。

## 3. 显存和速度

按服务控制组 PID 归属采样，约每 0.5 秒读取 NVML；下表为运行期间采样峰值，未单独捕获整个冷启动的瞬时最大值。

| 项目 | BF16 | FP8 |
| --- | --- | --- |
| 测试期间模型进程显存峰值 | **23.01 GiB** | **18.22 GiB** |
| 原图“桌面上有什么？”中位数，3 次 | 9.15 秒 | 7.89 秒 |
| 4MP 单路物品清单中位数，5 次 | 4.27 秒 | 4.04 秒 |
| 4MP 三路短字段 P95，15 次 | **3.92 秒** | **3.48 秒** |
| 4MP 三路完整清单 P95，9 次 | **7.49 秒** | **8.36 秒** |

FP8 减少约 **4.79 GiB／20.8%**。其刚加载、未做正式图片推理时的空闲读数约 16.77 GiB；不能拿该值替代工作后约 18.22 GiB 的预算，也不能直接套用其他配方的最低显存参考值。

FP8 并非所有负载都更快。原图开放描述的示例输出为 BF16 252 tokens、FP8 228 tokens，完整响应时差包含回答长度变化，不能全部归因于计算加速。三路完整清单在本轮反而更慢；三路短字段两端均 15/15 低于 5 秒。

本轮没有联合启动 FP8 和 VLA。将 FP8 18.22 GiB 与前一轮单 VLA 的 6.51 GiB 分别测得峰值相加，约为 24.73 GiB，尚未计其他程序；这只是估算，不能写成 FP8＋VLA 的联合实测，也不足以承诺 24GB 同卡部署。

## 4. 识别效果

| 检查 | BF16 | FP8 |
| --- | --- | --- |
| 约束 JSON 的标注题正确 | 54/57 | 54/57 |
| 无约束格式的标注题内容正确 | 18/19 | 18/19 |
| 无约束题严格裸 JSON | 14/19 | 14/19 |
| 三路短字段预定义内容正确 | 15/15 | 15/15 |

逐项配对未发现 BF16 正确、FP8 错误的新增标注退化，也没有发现新增通过项。两端仍将双视角空桌误计为 1；57 次中的 3 个失败是同一题的三次重复。无约束结果仍存在代码块，语义评分与严格 JSON 分开记录。

开放描述和物品清单文字有变化，没有逐项完整人工标注；不能将“本轮标注集无新增错误”外推成所有场景完全无损。拭子、真实交接、遮挡、细小文字和动作成功正例仍缺充分业务样本。

## 5. Connection 接入复验

通过现有五类图片入口，两端各 8 次，共 16 次真实模型调用：现场描述、Slaver 描述、双图桌面关系判断、抓放图像核验和候选物体识别。只改变测试进程中的端点，去掉云端密钥并阻止非本机图像模型请求。

- 两端均 8/8 正常返回，无长度截断，均使用本地占位鉴权。
- 可见但未抓住、抓取目标不存在、放置目标不存在三类核验字段均符合预定义结果，无新增负例失败。
- 同一张照片作为当前／标准图时，两端都没有建议 clean 或 organize；这不等于完整桌面整理准确率验收。
- 双图判断本轮耗时 BF16 13.38 秒、FP8 9.94 秒；其他小图调用约 0.2～1.0 秒。样本数量不足以给这些接口稳定时延承诺。

另经隔离 Brain HTTP 入口，临时切换实验工作区视觉端点，分别运行有物体／空桌的实时 MuJoCo 看图任务，共 4 次：BF16 约 0.664／0.462 秒，FP8 约 0.565／0.460 秒，均为 succeeded。任务成功表示取图和描述链路完成，不代表描述语义全部正确；没有执行机器人动作。实验配置已按原字节恢复，主工作区默认未修改。

## 6. 交付状态与证据

当前 Connection 默认仍使用 BF16。测试结束后停止独立的 FP8 服务，释放额外显存；保留权重、兼容目录、报告和 `launch_fp8.py`，默认候选端口为 18036。`--dry-run` 只预览启动参数，去掉后启动服务，不自动修改 Connection 路由。冗余下载分段已清理，失败日志和校验记录保留。

本次没有修改 Connection 源码机制，没有把此前 583＋27 项回归重复计入本轮。实际验证为 246 次视觉调用、官方完整文件哈希、兼容配置核对、实验配置恢复及模型服务收尾；文档执行链接检查与 `git diff --check`。

结论：这个发布版本可作为约省 4.8 GiB 的候选，在本轮小样本中没有新增标注错误；并不是所有任务更快，也尚未达到生产全场景替换验收。
