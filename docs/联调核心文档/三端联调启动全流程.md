# 三端联调启动全流程

日期：2026-09-17  
适用范围：从冷机到能发真机接待任务的完整启动顺序，含大脑侧进程、真机三端、人工闸门、验证点和收工顺序。  
细节分工：本机开箱、仿真四宫格、网页 / 飞书发任务见 [项目快速上手指南](../项目快速上手指南.md)。导航一键脚本与闸门口径见 [导航一键启动现场执行（当前版）](导航一键启动现场执行（当前版）.md)，VLA HTTP 边界见 [G1 Brain–VLA 桥接（当前版）](G1%20Brain–VLA%20桥接（当前版）.md)。本文只管顺序和判断标准。

## 1. 开机（大脑侧）

冷机只有面板自启，业务进程默认全停：

```bash
sudo systemctl status fqplanner-panel   # 不在就 sudo bash web/install_panel.sh
```

浏览器开 `http://192.168.5.35:5678`，按卡片顺序点「重启」：

1. **Redis** —— 协作底座，必须先活。
2. **Master** —— `:5000`，真正执行任务。重启会按 `collaborator.clear=true` 清空协作库，面板会先弹确认。
3. **Deploy** —— `:8888`，网页入口，把请求转给 Master。
4. 按需：**飞书桥接**（飞书入口）、**Slaver**（只有通用任务链要）、**Desk `:5008`**（通用任务 mock 后端）、**MuJoCo `:5001`**（几何仿真）、**3DGS `:5002`**（扫描场景看图，起来后优先于 MuJoCo）。

固定真机接待不经 Slaver 和 Desk，Master 直连 DREAM / VLA。每个服务一个 tmux session，名字就是服务 id（`tmux attach -t master`），日志统一在 `log/YYYY-MM-DD/<服务>/`。`systemctl restart fqplanner-panel` 只重拉面板本身（单元 `KillMode=process`），不会带走业务进程。

## 2. 起真机三端

**开始之前的物理前置**：机器人在支撑架上、肩带挂好、急停在人手里、MID-360 视野内无人靠近。这一条不满足就不要往下点。

面板 DREAM 卡片点「启动」，等价于导航机上 `bash tools/g1_three_party_oneclick.sh start`（目录 `<DREAM_ROOT>`）。面板把它跑在导航机 tmux 会话 `g1_panel_oneclick` 里，输出经 `pipe-pane` 落到导航机 `/tmp/fqplanner_dream_oneclick.log`，面板 `tail -F`，所以面板重启不带走编排、也不丢日志。要接手就 `tmux attach -t g1_panel_oneclick`。

脚本内部顺序是：网络自检 → NX SONIC（冷机在这里启控制器）→ 相机、灵巧手 → 4090 Brain HTTP 8091 与导航 relay 5556 → DREAM 定位工作流。人工闸门按出现顺序四道：

| 序号 | 闸门 | 超时 | 面板对应 |
| --- | --- | --- | --- |
| 1 | 输入 `READY` | 无 | 面板自动代填 |
| 2 | `adapter` 窗口第一次 Enter（接管，等同手柄 A+X+B+Y，肩带保持挂着） | **600 秒** | 点「站立 Enter」 |
| 3 | 同窗口第二次 Enter（进 POSE 站立，等 stage 1 稳定后再点） | **600 秒** | 再点一次「站立 Enter」 |
| 4 | `strap-check` 窗口回车（站稳、解肩带、视野清空后） | **600 秒** | 无按钮，必须人到导航机确认 |

闸门 2/3 的 600 秒是硬超时。超时会打 `POSE ready file was not created; navigation remains locked.` 并退出编排，此时机器人还能靠 Enter 站起来，但 `arm`、地图、孪生和 9882 都不会再起，只能 `stop` 后 `resume`。

过了第 4 道闸门，coarse 定位、孪生、9882 才会起来。

## 3. 9882 点初始位姿

9882 默认只 bind `127.0.0.1`，局域网直连是 `ERR_CONNECTION_REFUSED`。面板在启动时已把它转发到大脑机，就绪后会自动弹窗，也可以点卡片上的「打开 9882」，地址 `http://192.168.5.35:9882`。不用面板就自己开隧道：`ssh -L 9882:127.0.0.1:9882 dream`。

在页面上点机器人当前的初始位置和朝向，再 Approve。这一步永远是人工，面板不代点。Approve 之后定位收敛，8001 才真正可接任务。

## 4. 发任务前的只读预检

不发动作，先确认三端都在：

```bash
curl -s http://127.0.0.1:5000/api/task_status
curl -s -X POST http://127.0.0.1:5000/api/task_preflight \
  -H 'Content-Type: application/json' -d '{"task":"开始接待"}'
```

`task_preflight` 只读下游状态，不提交导航或抓放。`required && !ready` 时 Master 的 `POST /publish_task` 会直接返回 `status=rejected`，所以 DREAM 不通时，网页点和飞书确认都应该在日志里看到 `[task] preflight … ready=false`，而不是跑进接待 skill 再 `FAILED FETCHING_WORLD`。面板真机层两张卡片同时绿灯，是同一件事的可视化。

## 5. 发任务

两个入口，等价，都落到 Deploy `:8888` → Master `:5000`：

- 网页 `http://192.168.5.35:8888`。任务控制台四宫格是**当前仿真后端的四路相机**（不是四个仿真）：3DGS `:5002` 起来是扫描室内，否则 MuJoCo `:5001` 是几何厨房。直播是现渲，回放是该任务逐步截帧。
- 飞书私聊直接发，群里 `@机器人 /task <内容>`。运动类任务要原发送者确认；只读的「桌上有什么」不用确认。`LARK_TASK_MODE=dry_run` 只发卡不提交，`active` 才真发。

看执行过程：面板日志区或 `log/YYYY-MM-DD/master/`，正文看 `[task]` / `[reception]` 行，Flask 访问日志只有方法和路径。DREAM / VLA 的探测和 SSH 输出在当天的 `monitor.log`。任务结束后飞书卡片会带「复盘」摘要；账本在 `master/memory/reflections/`，不改真机 Pipeline。闲聊/预检日志不再沿用上一次 `task_id`。

真机接待中途失败（例如停在 `NAVIGATING_TO_RELAY2`，VLA 仍持有 `cola_can_1`）时：先修现场，再在 `:8888` 点 **断点继续**（`resume: true`），从 `failed_phase` 接着发，不重开、不重抓。不要再点「开始接待」走新任务预检——空手门会挡住持物状态。确认要整单重开时才用 `force_new_task`。细节见 [大脑侧实现说明 §9.1](01_大脑侧_单链路联调实现与接口说明.md)。

**证据等级**：当前 `vla_result_policy: hand_state_only`，三个照片验证开关都关。完整流程的终态是 `COMPLETED_HAND_STATE_ONLY`，只代表左手开合确认加至少 3 帧证据，**不等于**图像证实可乐在手上或已放到桌面。对外不要说成视觉验收通过。

## 6. 收工

顺序反着来：

1. 任务跑完或主动停任务，确认机器人不在动。
2. 面板 DREAM 卡片「停止」，等价 `g1_three_party_oneclick.sh stop`。它只关 DREAM 与 VLA 的 HTTP/relay，日志会打 `NX SONIC/camera/hand preserved`，机器人仍靠 SONIC 站着。面板同时收掉 `g1_panel_oneclick` 会话。
3. 机器人要坐下 / 控制器要退出，人到现场物理确认站稳后再 `bash tools/g1_fixed_map_relocalize_navigation_workflow.sh shutdown-sonic`。这条未经实跑验证，首次执行前先和导航组确认。
4. 大脑侧按需在面板停 Deploy / Master / Redis（顺序无所谓，但 Redis 最后）。面板本身留着。

只想重起操控侧而不动 SONIC / 相机 / 灵巧手：

```bash
ssh gpu4090
cd <VLA_PROJECT_ROOT>
BRAIN_VLA_REAL_ACTION_ACK=PHYSICAL_ESTOP_READY ./run_agent_vla_runtime.sh start
```

面板 VLA 卡片的启停就是这条，可以单独用。

## 7. 卡住时先看哪一条

| 现象 | 大概率原因 | 处理 |
| --- | --- | --- |
| 9882 打不开、`connection refused` | 只 bind 了 `127.0.0.1`，或第 4 道闸门还没过、web 窗口没起 | 用面板的转发 / 自己开隧道；确认 `strap-check` 已回车 |
| 编排报 `POSE ready file was not created` | 两次 Enter 超过 600 秒 | `stop` 后 `resume`，只重起 DREAM |
| 冷机停在 `SONIC status/safety attestation failed` | 4090 runtime 要求 SONIC 已持有 `rt/lowcmd` | 已由导航组把 SONIC 提到 bridge 之前，2026-09-17 16:03 起修复 |
| 启动早期 `Host key verification failed` | 旧脚本对退役的 Windows 大脑 `192.168.0.108` 做 SSH 探测 | 已由导航组默认跳过，需要时 `G1_CHECK_AGENT_SSH=1` |
| 面板日志停更但导航机还在跑 | 面板重启、`tail -F` 断了 | 刷新面板会重建 follower；原始日志始终在导航机 `/tmp/fqplanner_dream_oneclick.log` |
| 任务秒变 `rejected` | 预检判定 DREAM 未就绪 | 回到第 2–3 步，别在 Master 侧找原因 |
| 预检报仍持有 `cola_can_1` | 抓取后失败又点了「开始接待」 | 修现场后点「断点继续」，不要 `force_new_task` 除非整单重开 |
| Redis 里协作数据没了 | 重启 Master 会清协作库 | 别把重启 Master 当健康检查 |
