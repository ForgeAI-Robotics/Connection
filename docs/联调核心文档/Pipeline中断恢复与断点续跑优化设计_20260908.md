## 1. 目标与结论

保留“前置条件未满足，不执行依赖步骤”的原则，增加**有界等待、执行状态核查、持久化断点、恢复预检、受控重试与原任务续跑**。

优化后的预期体验：

~~~text
任务执行中
 → 子任务异常
 → 明确显示是哪一步、是否可能还在执行
 → 自动查询原命令或等待现场处理
 → 核实当前位置、持有物体和控制权
 → 恢复原任务
 → 从仍满足条件的步骤继续
~~~

“继续”不能简单实现为把当前步骤标记成功、清 busy 或重新发布整个任务。恢复需要同时回答：

1. 原命令是否已经执行、是否仍在执行、是否已可靠停止？
2. 已完成步骤的证据是否足够，当前现场是否还满足下一步的前置条件？
3. 下一步应重新跟踪原命令、重试当前步骤，还是调整计划？
4. 本次恢复是否已经被其他请求处理，是否会重复产生动作？

### 1.1 第一版范围

- 优先覆盖当前单机器人、严格串行执行场景。
- 同时考虑 LLM 拆解后的通用任务与固定真机接待。
- 先解决错误等待和状态误判，再做人工确认续跑，最后开放有限自动恢复。
- 不要求第一版引入大型工作流框架或并行 DAG 调度器。
- 不修改模型权重、低层电机控制、已验证导航算法。
- 不将网页操作、网络重连或进程重启替代为现场审批。
- 本次只编写设计文档，不修改业务代码、配置和机器人服务。

### 1.2 依据与不确定性

本文核对的是 2026-09-08 本地工作区源码，文件位置见第 18 节。两条大脑调用路径已通过代码确认。

已于 2026-09-08 通过 SSH 只读核对导航侧 `fq@192.168.5.185` 与 VLA 侧 `lgj_4090@192.168.5.194` 的任务服务、取消处理、持久化、hook 收尾和动作 relay。第 17 节区分实查能力与拟新增能力，附录 C 记录文件版本。

本次核验属于源码分析，没有运行故障注入或机器人动作测试。源码中的停止字段、进程检查和端口状态不等于已经做过现场物理停止验收；拟新增字段和 API 仍未实现。后续实施应再次核对源文件版本，避免使用桌面旧副本覆盖远端更新。

先前观察到的故障（如 NX 反馈 stale、HTTP 超时）仅作为场景，不认定所有中断都由同一原因造成。

### 1.3 v1.2 的关键方案调整

1. **导航侧补“读取恢复”，而不重复造已有日志。** 保留现有命令与事件格式，增加稳定存储、启动重建和原命令查询。启动快照写入必须在恢复完成后进行。
2. **VLA 保留已有重启保护，增加受控核查和解除流程。** 不能只把 `recovery_required` 改为 false，也不能对所有旧任务重新运行 worker。
3. **取消和停止拆成两阶段。** 接受停止请求后保持 CANCELLING；下游停止证据满足后才终结和释放资源。
4. **5556 使用带身份的交接事务。** 将命令 ID、事务 ID、relay 实例、代次带入请求与响应，避免无身份 Bool 被当作本轮确认。
5. **动作出口归还与手部目标分离。** 取消/失败的归还不自动代表应保持握拳；必须保留或重新确认持有状态。
6. **实施先补下游基础，再做大脑续跑。** 大脑无限等待/误判修正可独立先做，但跨重启续跑必须等待导航恢复、VLA 隔离及交接合同验收。

## 2. 当前两条调用路径

### 2.1 LLM 拆解后的通用任务

~~~text
POST 8888 /publish_task
 → Master publish_global_task()
 → LLM 拆解任务
 → TaskQueue
 → Master 逐个通过 Redis Pub/Sub 发给 Slaver
 → Slaver 调用 MCP / Robot API 工具
 → 返回子任务结果
 → Master 决定下一步
~~~

当前控制点：

- `master/agents/agent.py::TaskQueue`
- `GlobalAgent.publish_global_task()`
- `GlobalAgent._dispath_subtasks_async()`
- `GlobalAgent._handle_result()`
- `agent/collaboration/collaborator.py::wait_agents_free()`
- `slaver/run.py::_execute_task() / _send_result()`

使用 DREAM 后端时，某个子任务明确返回 failure、exception 或 timeout，Master 会将剩余任务标记失败并退出调度。非 DREAM 路径保留部分诊断、重插队列和重规划逻辑，不能把两者视为完全相同策略。

### 2.2 固定真机接待

~~~text
POST 8888 /publish_task
 → Master 接待分支
 → ReceptionRealRunner
 → DREAM table2
 → VLA pick
 → DREAM relay2 / relay3 / table1
 → VLA place
 → 结果验证
~~~

这条路径由 Master 内的固定流程直接调用 DREAM/VLA HTTP，不逐步经过 Slaver。它目前是长函数顺序执行，异常统一进入 FAILED 或 RECOVERY_REQUIRED。

两条路径应共用执行身份、持久化记录、错误分类和恢复规则，但保留各自执行适配器，避免重构时改变现有任务语义。

## 3. 已确认的问题与修改方向

| 编号 | 当前实现 / 证据 | 后果 | 优化方向 |
| --- | --- | --- | --- |
| P01 | 通用调度和拍照任务调用 `wait_agents_free()` 未传 timeout；默认无超时 | Slaver 退出或结果丢失后可能无限等待 | 每次执行有期限，超时进入核查状态 |
| P02 | 未检查等待函数返回值；`_last_subtask_status or "success"` | Redis 异常、缺失结果可能被记成成功 | 完整终态证据是成功的唯一依据 |
| P03 | `_handle_result()` 识别旧 task_id 后仍清除机器人 busy | 旧结果可能影响新任务等待 | 按 task/step/attempt/owner 精确匹配 |
| P04 | 同一 task 内用共享 `_last_subtask_status/result`，没有完整 attempt 身份 | 重复、迟到结果可能串到下一子任务 | 每次执行独立结果槽与状态记录 |
| P05 | `publish_global_task()` 新任务使旧线程 token 失效，并清所有机器人 busy | 本地停止调度不能证明远端动作停止 | 新动作任务必须通过资源准入检查 |
| P06 | Redis Pub/Sub 发送结果未由调度器可靠处理；消息本身不持久 | 未接收与执行中失联难以区分 | 持久发送意图、接收确认、执行结果查询 |
| P07 | 固定接待是一段长顺序函数 | 不能选定恢复入口并复用已完成结果 | 显式 step runner + 检查点 |
| P08 | `RECOVERY_REQUIRED` 被放入允许新任务初始化的终态集合 | 待恢复本地状态可被后续初始化覆盖；远端预检可能再阻挡，但历史已丢 | 业务终态与资源已清理分离 |
| P09 | 当前持久化主要是单份 current_task.json、公共事件和固定图片名 | 新任务/新尝试可能覆盖旧状态与图片；多实例锁不充分 | 按任务/尝试持久化，事务提交证据 |
| P10 | `_command_id()` 用 task_id 尾部 token + 步骤前缀；`commands[key]` 仅一个记录 | 同一步真实重试难以区分新旧尝试，历史被替换 | 稳定 step_id，多 attempt、多 command 映射 |
| P11 | 新任务预检要求 holding=null，固定结果文案存在 vla_only | 直接复用预检会阻挡抓取后的合法续跑；证据粒度不够 | 按步骤重建条件，保存明确证据等级 |
| P12 | 本地等待终态超时抛普通错误；主流程未统一确认取消完成 | 本地 FAILED 不证明远端动作已停 | 超时进入 RECONCILING/CANCELLING，核清前保留资源 |
| P13 | Master/Deploy 缺少完整恢复/续跑/取消生命周期接口 | 用户只能反复点击开始接待 | 明确区分新建、检查恢复、续跑、结束本轮 |
| P14 | get_task_status 的 active/all_done/failed 与执行状态混合，网页据此显示进度 | 待恢复可能被显示为已结束或无法继续跟踪 | 后端新状态字段和网页兼容映射一起升级 |

该表是大脑侧问题清单；两侧 SSH 核验补充的 R01–R20 见第 17.1 节。开发排期必须合并看两张表，不能把下游恢复能力当作已经完成。

### 3.1 关于当前 motion_ready 的特殊情况

当前 `_collect_preflight()` 已允许一种“定位批准、传输就绪、无活动命令，但处于未 arm 待机”的情况：motion_ready=false，且 blockers 是 Gateway/Token 未就绪集合中的非空子集。

因此新设计不能简单规定“所有情况下 motion_ready=false 一律失败”，也不能仅凭这两个 blocker 就假设没有真实故障。

建议在协议中增加明确 `can_accept_navigation_goal` 或结构化 standby reason，区分：

- **允许接收目标的未 arm 待机**；
- **实际反馈异常、传感器过期或保护锁定**。

第一版若下游没有该能力，保持已有经过审核的接收合同，记录其适用版本和限制；真正开始运动仍必须由 DREAM 内部完成放行，Master 不直接 arm。

## 4. 设计原则与必须成立的约束

| 约束 | 实现要求 |
| --- | --- |
| 未收到响应不等于未执行 | 超时优先查询原命令，不能自动生成新命令 |
| busy 只是占用视图 | 不以 busy=false 或 key 缺失判成功 |
| 历史事实与现场条件分开 | 过去导航成功不代表机器人现在仍在那里 |
| 成功需要证据 | 身份、业务结果、必要后置条件与证据策略全部通过 |
| 中断后不盲目重发 | 查询、重新跟踪与重新执行采用不同操作 |
| 原子接收恢复请求 | 同一 revision 下两个 resume 最多接受一个 |
| 只有一个业务重试决策者 | Master 统筹预算；下游内部恢复需报告结果 |
| 资源占用不能靠超时自动消失 | 租约过期后进入隔离/核查，不等于允许新动作 |
| 终止不是仅清 UI | 取消下游并确认停止/交还后才关闭任务 |
| LLM 不能伪造完成证据 | LLM 给建议；确定性规则审核与执行 |
| 不承诺跨进程物理 exactly-once | 通过幂等身份、持久意图、核查与互斥降低重复执行；无法确认时停在未知状态 |

## 5. 目标架构

~~~text
8888 网页 / 本地 HTTP 任务入口
                 │
                 ▼
Master API：准入、幂等、恢复检查、resume、cancel
                 │
                 ▼
TaskCoordinator：计划与状态迁移、资源锁、重试预算
        ┌────────┴───────────┐
        ▼                    ▼
通用步骤执行器           固定接待步骤执行器
        │                    │
Redis + Slaver           DreamClient / VlaClient
        │                    │
MCP / Robot API          DREAM / VLA 原命令
        └────────┬───────────┘
                 ▼
统一结果格式 → 证据验证 → 持久事务 → 下一步条件检查
                 │
                 └─ 异常 → RecoveryManager → 原命令核查 / 恢复建议
~~~

新增共享层负责状态与恢复，业务层负责“某一步怎样执行、什么才算完成”。不要同时保留两个会各自推进同一任务的独立调度循环。

第一版仍是一台机器人一个动作任务。只读查询可以并存，但也要受资源/接口能力限制；未知 MCP 工具默认不能因为名字像查询就认定无副作用。

## 6. 任务、步骤与执行尝试的身份

| 字段 | 语义 | 何时改变 |
| --- | --- | --- |
| task_id | 整个用户任务 | 新建任务时；恢复原任务保持不变 |
| plan_revision | 任务计划版本 | 经审核修改尚未执行部分时 |
| step_id | 逻辑步骤，如 nav_table2 / pick_cola / nav_relay2 | 新逻辑步骤才新建 |
| attempt_id | 一次具体执行尝试 | 确认允许重新执行当前步骤时 |
| attempt_no | 该步骤第几次执行 | 真实重试递增，查询重试不递增 |
| command_id | 该尝试对应下游命令 | 创建尝试时生成并持久化 |
| operation_id | 一次 publish/resume/cancel 请求的幂等键 | 同一次请求超时重试保持不变 |
| state_revision | 任务状态乐观锁版本 | 每次有效事务迁移递增 |
| worker_session_id | Slaver 本轮进程实例 | Slaver 重启改变 |
| ownership_epoch | Master/执行器的资源控制代次 | 经核准切换执行者时改变 |

command_id 推荐由完整 task_id、step_id、attempt_id 的稳定映射生成，满足下游长度/字符限制；不要只取任务尾部 12 位作为唯一身份依据。

一旦某 attempt 可能已经发送，其 payload 与摘要不再修改。改变目标、导航凭证或动作参数，必须先核清旧尝试，再生成新的 attempt。一个 step 可以包含多个工具调用，下游 command 则归属于该 attempt 的子调用记录，不能丢失对应关系。

### 6.1 同一个 ID 应如何重试

- **查询重试**：同 command_id，只 GET。
- **确认丢失但下游正在运行**：同 attempt，恢复查询与等待。
- **请求幂等重投**：只有下游明确声明并验证相同 ID + 相同 payload 的持久去重能力时才可使用。
- **业务重新执行**：旧 attempt 已有明确停止/未执行证据，条件与预算通过后，新 attempt、新 command_id，task/step 不变。
- **换一条路线或改目标**：属于计划修改；保存 plan_revision，不能覆盖旧 command 的输入。

## 7. 状态机设计

### 7.1 任务级状态

| 状态 | 含义 | 是否允许自动下发下一步 |
| --- | --- | --- |
| CREATED / PLANNING | 已接收任务，尚未执行 | 否 |
| READY / RUNNING | 可调度 / 正在执行 | 仅当前依赖与资源条件通过时 |
| WAITING_DEPENDENCY | 等待服务/传感条件恢复 | 只自动观察；动作恢复受配置控制 |
| RECONCILING | 正在核查旧命令是否执行 | 否 |
| RECOVERY_REQUIRED | 需要人工处理或恢复确认 | 否 |
| CANCELLING | 已请求取消，尚未确认停止 | 否 |
| SUCCEEDED | 严格证据策略下完成 | 无后续步骤 |
| COMPLETED_HAND_STATE_ONLY | hand-only 策略下完成 | 无后续步骤 |
| FAILED | 已决定结束，远端执行情况和资源处置已核清 | 否 |
| CANCELLED | 取消已完成，相关动作已确认停止 | 否 |

终态与资源策略：

- RECOVERY_REQUIRED、RECONCILING、WAITING_DEPENDENCY、CANCELLING 都不是业务终态。
- 若现场动作状态未知，即使放弃自动恢复，也不能把任务改成可释放资源的 FAILED。
- 增设 `execution_state_known`、`resources_released`、`blocks_new_motion`，避免用一个 status 同时表达所有含义。
- 人工关闭展示记录不等于解除设备隔离；若支持此操作，独立保存 unresolved resource incident。
- 新任务准入以资源处置与现场前置条件为准，不仅检查旧任务是否终态。比如上一任务正常结束但手仍持有物体，新 pick 仍须拒绝。

### 7.2 步骤和尝试

建议步骤状态：

~~~text
PENDING → READY → RUNNING → VERIFYING → SUCCEEDED
                    │           │
                    └──异常─────┴→ RECOVERY_REQUIRED
                                     │
                           核查成功 ──┤→ VERIFYING
                           确认重试 ──┤→ READY（创建新 attempt）
                           修改计划 ──┤→ INVALIDATED / 新步骤
                           结束本轮 ──┘→ FAILED / CANCELLED
~~~

尝试状态更精确：

`PREPARED → DISPATCHING → ACCEPTED → RUNNING → SUCCEEDED / FAILED / CANCELLED`。

任意“可能发出但没有可靠终态”的尝试进入 `UNKNOWN`。UNKNOWN 保留 command_id、最后观测和资源占用；不能自动重置成 PREPARED。

后续步骤在前置失败时标记 BLOCKED，并注明 blocked_by，而不是把未执行步骤伪装成执行失败。仅经规则确认无需执行的步骤可用 SKIPPED，并记录原因。

### 7.3 成功和后置条件

逻辑步骤推进必须满足：

~~~text
正确的执行身份
 + 对应业务成功证据
 + 满足证据等级
 + 当前所需资源/策略停止条件
 + 当前下一步前置条件
~~~

状态 VERIFIED 只是证据校验完成，不能用“LLM 认为成功”替代真实结果。业务成功但资源未归还，可以保留“效果已确认”，步骤停在 VERIFYING/BLOCKED，避免重复动作。

## 8. 持久化与崩溃恢复

### 8.1 推荐存储

第一版使用 Master 本机 SQLite（WAL、显式事务、foreign_keys 开启、busy_timeout），替代只依赖 current_task.json。数据库不放网络共享盘，不写入 Git。

| 表 | 核心字段 |
| --- | --- |
| tasks | task_id、request_digest、task_type、state、state_revision、plan_revision、active_step_id |
| steps | task_id、step_id、ordinal、operation、requires、effects、status、retry_policy |
| attempts | attempt_id、step_id、attempt_no、payload_digest、state、remote_instance_id、timestamps |
| commands | service、command_id、attempt_id、request、latest_result、effect/stop/ownership evidence |
| events | event_id、task_id、sequence、type、payload、created_at |
| evidence | evidence_id、step/attempt、level、artifact_path/hash、validity_context |
| resource_owners | robot/resource、task/attempt、ownership_epoch、lease、quarantined |
| operations | operation_id、request_digest、kind、status、response |
| outbound_intents | command identity、payload、dispatch_state、dispatch timestamps |
| recovery_checks | check_id、task revision、plan revision、evidence summary、expires_at |

`ReceptionStore` 可以保留作为兼容层，将 current_task.json 导出为只读展示快照；SQLite 是唯一权威源，不能数据库/JSON 两边各自修改。

Slaver 保留独立本机执行记录，用来在结果消息丢失或进程重启后查询“我是否接收过并执行了这个 attempt”。不要共享同一个 SQLite 文件跨机器写入。

### 8.2 必须覆盖的崩溃窗口

| 崩溃发生点 | 重启后处理 |
| --- | --- |
| PREPARED 已落盘，尚未进入 DISPATCHING | 确认发送器从未领取后，按准入规则重新调度同一尝试 |
| 已进入 DISPATCHING，但不知是否发出 | UNKNOWN，查询原 command；不能因没有 sent 标记就假设没发 |
| 下游已接受，本地尚未记录响应 | 查询原 command，重建 ACCEPTED/RUNNING |
| 下游已完成，本地尚未提交成功检查点 | 找回证据并原子提交；不重做动作 |
| 检查点已提交，下一步尚未发送 | 核查当前现场后，从下一逻辑步骤继续 |
| 取消请求发出后崩溃 | 恢复取消状态核查；未确认停止前仍阻挡新动作 |

发送意图表不是“断电后把所有消息再发一遍”的队列。只有严格证明从未发送，或对端持久幂等合同有效时，才允许重投。

### 8.3 事务和证据有效期

- 同一事务写入结果、步骤迁移、任务 revision、事件与下一步索引。
- 照片先保存为不可变文件并计算 hash，再提交数据库引用；落盘失败不能记成功。
- 文件按 task/step/attempt 隔离，如 `runtime/tasks/<task>/evidence/<step>/<attempt>/`。
- 原子文件替换防半写，但不解决多个 Master 实例或线程的调度竞争；需要事务约束和进程实例控制。
- 历史证据不删除。地图变更、机器人移动、定位重新初始化、物体人工移除可能使它不再支持当前动作；另存失效原因。
- 运行内时限用 monotonic；跨重启用持久时间与启动代次重建，不直接复用上次 monotonic 数值。重启不能把重试预算清零。

## 9. Master 与 Slaver 的可靠执行协议

### 9.1 最小消息合同（拟议）

~~~json
{
  "schema_version": "brain/execution/v2",
  "task_id": "task-example",
  "plan_revision": 1,
  "step_id": "nav_table2",
  "attempt_id": "attempt-example",
  "attempt_no": 1,
  "robot_id": "FQrobot",
  "ownership_epoch": 7,
  "command_id": "nav-example",
  "operation": "navigate",
  "payload_digest": "sha256-example",
  "args": {"target_id": "table_2"}
}
~~~

Slaver 事件回复使用同一组 ID，并增加 `worker_session_id`、`event_id`、`sequence` 和事件类型：

- `ACCEPTED`：已持久接受，尚不代表开始动作；
- `RUNNING / PROGRESS`：执行状态，不能仅靠进程心跳冒充；
- `TERMINAL`：明确状态、结构化错误、结果与下游命令；
- `STATUS_RESPONSE`：对原 attempt 的查询响应。

通信字段由执行层添加，不让 LLM 拼写 task_id/command_id。MCP 工具返回必须保留结构化下游结果，而不只返回自然语言“失败了”。

### 9.2 Redis 的使用

第一阶段可以保留 Pub/Sub 作为通知通道，同时增加 Slaver 持久记录及状态查询机制；发送成功只说明消息发布，不证明被执行。

若没有可靠的持久接收记录、幂等和原状态查询，第一阶段只做到超时显式转待恢复，**不开启自动动作重投**。

后续可迁移 Redis Streams + consumer group，保存请求/事件；它提供可重投消息，仍不能保证物理动作只执行一次。重投必须先由 Slaver 按 attempt 去重并核查下游。业务接受/结果写入成功后再 ACK；不能 ACK 后再保存唯一结果。

### 9.3 busy 与资源租约

- 调度权记录带 robot、task、attempt、ownership_epoch。
- 获取/释放用原子 compare-and-set，而不是无条件写 true/false。
- 收到不匹配、缺 ID 或旧 worker 的结果，仅记录审计，不改变当前 busy。
- 租约到期或 worker 心跳丢失：标记疑似失联并隔离资源，查询其下游命令。
- **禁止租约一过期就启动新机器人任务**：旧工具或硬件动作可能仍运行。
- 如果下游支持 epoch fencing，要求拒绝旧代次动作；没有该能力时，只能靠停止确认和单执行器约束，不宣称已防止所有双主冲突。

### 9.4 必须修改的调度代码

`master/agents/agent.py`：

- 删除真实执行路径中“缺结果默认 success”。
- 检查发送与等待结果，等待必须支持 deadline 和 cancellation signal。
- 将共享 last result 改为 attempt 索引的执行记录/事件。
- 拍照诊断也纳入统一等待与身份机制。
- 新任务不得清空所有机器人 busy；旧调度线程失效不等于远端取消。
- 失败后下游任务保留 BLOCKED；恢复后依赖重新满足才重新成为 READY。

`slaver/run.py`：

- 先持久去重接受，再调用 MCP，完成后先存结果再发事件。
- 外层 try/except/finally 记录进程内异常、执行阶段与结构化失败。
- finally 可以关闭本地句柄，但不能无条件宣称物理动作停止或释放资源。
- 进程重启后优先核查未完成 attempts，不重新调用工具。
- 心跳同时区分 worker liveness 与 attempt progress；当前 30 秒一次心跳不能代替子任务时限。

`serve_dream/runtime/current_agent_task.json`：

- 当前单个上下文文件在多尝试/恢复时可能被覆盖。
- 优先显式传递 execution context；若 MCP 接口暂时无法扩展，使用不可变 attempt 路径并校验所持代次。
- `slaver/robot/module/base.py`、`robot_api/runtime.py`、`serve_dream/service/server.py` 一路传递持久 command_id，不在末端临时生成不可追踪的新 UUID。


## 10. 错误分类、时限与恢复策略

### 10.1 统一错误格式（拟议）

~~~json
{
  "category": "OBSERVATION_LOST",
  "code": "REMOTE_STATUS_TIMEOUT",
  "source": "dream",
  "message": "原导航命令状态连续无法确认",
  "execution_certainty": "UNKNOWN",
  "effect_state": "UNKNOWN",
  "stop_state": "UNKNOWN",
  "ownership_state": "UNKNOWN",
  "command_id": "nav-example",
  "retry_class": "QUERY_ONLY",
  "last_observed_remote_state": "running",
  "observed_at": "2026-09-08T10:00:00+08:00",
  "raw_error_ref": "event-example"
}
~~~

建议分类：

| 分类 | 例子 | 默认动作 |
| --- | --- | --- |
| DEPENDENCY_UNAVAILABLE | 服务未起、模型依赖未就绪，且明确未开始 | 等待依赖，核查后按策略提交 |
| DELIVERY_UNKNOWN | POST 超时、连接重置 | 查询原 ID |
| OBSERVATION_LOST | 原任务已接受，但状态查询断线 | 保持原 attempt，恢复跟踪 |
| EXECUTION_FAILED | 下游明确失败 | 检查停止证据与业务状态 |
| CONTRACT_MISMATCH | ID、目标、map、结果字段不符 | 待人工处理，不重试动作 |
| ENVIRONMENT_CHANGED | 物体被拿走、机器人移动、路径失效 | 当前条件重建，必要时改计划 |
| SAFETY_STOP | 急停、姿态/反馈保护、控制权冲突 | 待现场处理 |
| EXECUTOR_LOST | Slaver 退出、MCP 失联 | 核查已派发的下游命令 |
| EVIDENCE_INSUFFICIENT | 抓取完成但证据不足 | 先补证据，不直接再抓 |
| INTERNAL_ERROR | 代码异常、存储失败 | 依据发生阶段判定执行是否未知 |

HTTP 4xx/5xx 或 `retryable=true` 不能独立决定是否重执行。尤其 500/504 可能发生在动作已经开始后；404 也可能表示记录过期、服务实例更换或存储丢失，而不是从未执行。

### 10.2 分离各类时限

| 参数 | 用途 | 第一版建议 |
| --- | --- | --- |
| request_timeout_sec | 单次 HTTP 请求上限 | 保留现有约 10 秒作为起点，依据现场数据调整 |
| acceptance_timeout_sec | 等待 Slaver 持久接收确认 | 5 秒候选值 |
| progress_stale_sec | 多久无新的执行进度 | 按工具分类；进程活着不刷新此项 |
| execution_timeout_sec | 单次物理/业务步骤执行预算 | 导航、模型加载、抓取分开配置 |
| reconcile_budget_sec | 自动查询原状态的总预算 | 30 秒候选值，耗尽转待恢复 |
| operator_wait_timeout_sec | 人工确认等待 | 到期保持待恢复或进入受控取消，不自动执行 |
| cancel_confirmation_timeout_sec | 等待远端停止证据 | 15 秒候选值，耗尽仍视为未知 |
| task_execution_budget_sec | 整个任务执行总预算 | 包含所有真实尝试与下游内部恢复 |
| task_elapsed_limit_sec | 含人工等待的总生命周期限制 | 单独配置，到期也不能直接释放未知动作资源 |

候选数值是设计建议，不是验收结果。嵌套请求需使用 `min(单次上限, 当前阶段剩余预算)`，防止三个 10 秒调用突破 15 秒核查预算。禁止无限 while 和无上限指数退避。

### 10.3 哪些动作可自动恢复

| 情况 | 第一版策略 |
| --- | --- |
| 只读 GET 瞬时失败 | 有限退避重查 |
| 原 command 查询重新可用，仍 running | 重新附着跟踪，不发送动作 |
| 原 command 已 succeeded，证据完整 | 提交检查点；下一个有副作用步骤是否自动启动由恢复策略决定 |
| 原请求明确未接收/未开始 | 条件恢复后允许按预算重新提交 |
| 导航明确失败并停止 | 默认人工确认；后续只对白名单错误开放一次自动重试 |
| 抓取/放置已开始后失败 | 第一版人工确认及现场核查，不自动重做 |
| 动作成功但照片验证失败 | 允许重试证据获取/验证；不能据此自动重抓/重放 |
| 急停、定位批准失效、NX 反馈 stale | 仅观察条件恢复；不自动解除保护或审批 |
| 持有状态矛盾 | 人工核对并形成新事实记录；不能直接清 holding |
| 原命令找不到且执行未知 | RECOVERY_REQUIRED，不能当作未执行 |

查询重试、模型请求重试、下游内部动作恢复和 Master 业务重试分别计数，但受统一总预算约束。第一版动作重试默认人工确认；恢复“查询”不需要等同于恢复“运动”。

## 11. 固定接待如何改为可续跑步骤

### 11.1 步骤定义

| step_id | 执行器 | 关键前置条件 | 完成/推进条件 |
| --- | --- | --- | --- |
| preflight_initial | 只读检查 | 新任务无未解决资源占用 | 初始世界/服务/图合同与空手条件满足 |
| nav_table2 | DREAM | 定位批准、可接收目标、动作出口归导航 | 对应导航成功、停止证据；当前位置支持抓取 |
| inspect_table2 | DREAM，可选 | 开启细检且双方合同支持 | 细检终态与相机交接证据；navigation-only 时按配置合法跳过 |
| pick_cola | VLA | 有效 table2 导航凭证、空手、相机/策略条件 | pick 证据通过，策略停止、端口归还 |
| verify_pick | 可选验证 | 原 pick 已有明确结果 | 满足配置的证据策略 |
| nav_relay2 | DREAM | 持有目标物体的当前证据满足策略；可导航 | 门外接近完成 |
| nav_relay3 | DREAM | relay2 后置条件、当前位置/朝向可执行横移 | 横移完成与停止 |
| nav_table1 | DREAM | 门段依赖满足、仍持有目标 | 到 table1 并停止 |
| place_cola | VLA | table1 凭证有效、持有物体、必要操作批准 | place 证据、策略停止、端口归还 |
| verify_place | 可选验证 | 原 place 已结束 | 满足照片/物体策略或明确 hand-only 结果 |
| finalize | 本地事务 | 所有必要步骤完成、资源处置已核清 | 对应证据等级的终态 |

不要将所有步骤都套用 `holding=null`。初始/pick 需要空手；pick 后导航/place 需要持有；place 后验证/finalize 通常需要已释放。

hand_state_only 模式应保存“根据手状态推定持有”，包括证据来源和等级；不能将该模式推定升级为物体真实存在。若人工观察与推定冲突，必须先处理冲突。

### 11.2 拆分现有长函数

建议新增：

- `build_reception_plan(config)`：产生固定步骤与依赖。
- `execute_step(step, attempt, context)`：仅执行一个步骤。
- `verify_step_result(step, attempt, result)`：验证终态与后置条件。
- `reconcile_attempt(attempt)`：只查询原命令。
- `check_step_preconditions(step, facts)`：当前步骤级预检。
- `resume_task(task_id, expected_revision, operation_id)`：协调恢复。
- `cancel_task(task_id, operation_id)`：统一取消生命周期。

现有 `_navigate()` / `_vla_action()` 改为接收已经持久化的 attempt 和 command_id；不得在它们内部隐式生成下一次身份。

`_start_state()` 只负责新任务创建；`load_for_resume()` 读取原任务，不能清空 commands、holding、verified_state 和历史尝试。

### 11.3 断点选择算法

1. 按 task_id 加载任务计划、所有尝试和最后已提交检查点。
2. 检查是否存在 UNKNOWN、ACCEPTED、RUNNING、CANCELLING 尝试。
3. 若存在，优先查询其原命令；核清前不选新执行步骤。
4. 对已完成步骤保留历史事实；重新采集将要执行步骤需要的现场条件。
5. 找到最早“未完成或当前条件已失效”的必要步骤。
6. 生成恢复计划：重新跟踪 / 重试该步骤 / 补验证 / 追加准备步骤 / 人工处理。
7. 记录计划摘要和依据，展示给操作人或交给已批准的有限自动策略。
8. 执行 resume 时重新检查状态版本和最新现场条件，再原子领取执行权。

“最早失败步骤”并不总是恢复点：如果机器人被拖动，可能需要先重新定位；如果已经放下物体但本地漏记结果，恢复点可能是 verify_place 而不是 place。

### 11.4 导航凭证与路线版本

当前 VLA 请求引用成功导航 command_id。导航重试成功后必须使用**新的成功凭证**，不能沿用失败尝试的 ID。

建议绑定地图 hash、定位会话、审核路线版本、目标和到位时间。保存：

- 历史导航成功：永久事实；
- 当前仍在目标位姿：有时效的现场条件；
- 凭证能否用于此次操作：由下游合同验证。

map 或路线改变时，先做合同重新对齐；不能自动改大脑硬编码坐标来“通过检查”。不同路线版本的门段证据不能无条件拼接。

远端实查进一步确认：导航的门段依赖来自其内存 commands 表，当前重启后不会恢复。所以跨重启恢复 relay2/relay3/table1 的前置条件之一，是导航侧先恢复自己的原成功记录。大脑仅传入同一 task_id 并不够，也不能伪造一次导航成功来补记录。

## 12. 三种核心恢复场景

### 12.1 table2 导航失败，尚未抓取

~~~text
nav_table2 attempt-1 → 明确失败
 → 确认停止、位置与定位状态
 → 等待反馈/保护条件恢复
 → 恢复检查通过并确认
 → nav_table2 attempt-2，新 command_id
 → 导航成功
 → pick 使用 attempt-2 的成功凭证
~~~

若 NX 反馈仍 stale，停留待恢复；“接口通了”不能证明动作链恢复。

### 12.2 pick 已成功，relay2 导航失败

~~~text
nav_table2 成功
pick 成功（证据等级已记录）
nav_relay2 attempt-1 失败
 → 确认原导航停止
 → 核查当前持有、定位、相机/反馈和动作所有权
 → nav_relay2 attempt-2
 → nav_relay3 → nav_table1 → place
~~~

不重做 pick。若物体已取下，原任务语义发生变化：必须产生人工事实修正与重新规划/结束决策。不能靠清空 VLA holding 继续搬运一件已经不在手中的物体。

若中间重启过导航或 relay，必须分别核查：导航已加载 table2 成功历史；VLA holding 的证据仍适用；relay 的 owner 和 carry 策略已重新建立。任一项未核清，继续按钮应显示具体 blocker，而不是重新执行 pick。

### 12.3 place 可能成功，但响应丢失

~~~text
place 请求结果未知
 → 按原 command_id 查询
 ├─ still running → 继续跟踪
 ├─ succeeded + 证据完整 → 检查点提交，再验证/结束
 ├─ failed + 停止已确认 → 评估已释放/仍持有情况
 └─ 找不到/长期不可达 → RECOVERY_REQUIRED
~~~

“手已张开”不自动等于“可乐已放在 table1”，应依照既定证据等级决定终态。证据不足优先补观测，不重复执行 place。

## 13. 通用 LLM 任务的恢复和局部重规划

### 13.1 扩展计划格式

现有纯自然语言 subtask 增加结构化操作、依赖与条件。示例：

~~~json
{
  "step_id": "place_cola",
  "operation": "place",
  "executor": "vla",
  "depends_on": ["nav_table1", "pick_cola"],
  "requires": [
    {"fact": "at_target", "value": "table_1"},
    {"fact": "holding", "value": "cola_can_1"}
  ],
  "effects": [
    {"fact": "released", "value": true}
  ],
  "retry_policy": "operator_review",
  "evidence_policy": "hand_state_only"
}
~~~

LLM 可提出这些字段，但系统必须按操作注册表验证 executor、参数、依赖和证据策略。不能让模型定义任意可执行 shell、取消保护检查或选择比任务要求更低的证据等级。

复合子任务“走到桌边并抓取”应在持久动作边界拆成导航与抓取，或记录内部子调用检查点。否则前半步成功、后半步失败时，整个工具重试可能重复前半步动作。

### 13.2 允许 LLM 决策的范围

可以提出：重新观察、选择经批准的备用路线、缩小搜索范围、在当前语义允许下更换目标、增加准备步骤。

不能自行决定：

- 把未知执行状态改为成功/失败；
- 把已完成抓取加入重试队列；
- 在旧命令仍可能执行时发新动作；
- 清空 holding、解除急停、批准定位；
- 改地图坐标或控制参数绕过合同；
- 重试无上限。

### 13.3 局部重规划流程

1. 冻结当前调度，核清所有未完成动作。
2. 传给 LLM：原目标、当前结构化事实、已完成步骤证据、原始错误、可用能力与剩余预算。
3. 返回候选计划差异，不能覆盖历史计划。
4. 校验：无环、合法动作、依赖满足、无重复副作用、资源不冲突、证据等级不降级。
5. 真机高风险计划变化需要按现场策略确认。
6. 原子增加 plan_revision，并使旧 recovery_check 失效。
7. 仅调度新计划中通过准入的步骤。

第一版可以不用 LLM 自动恢复，只先支持固定规则和人工续跑；LLM 局部重规划在身份与检查点稳定之后接入。

## 14. 新接口、响应与并发控制

以下接口为**拟新增**，由 Master 实现业务规则，8888 仅代理。不能直接假设当前服务已有。

| 接口 | 用途 | 是否产生动作 |
| --- | --- | --- |
| `GET /api/tasks/{task_id}` | 按 ID 查询任务，不只返回全局 current | 否 |
| `GET /api/tasks/{task_id}/events?after_seq=N` | 增量事件 | 否 |
| `POST /api/tasks/{task_id}/recovery-check` | 查询下游并生成恢复检查结果 | 不发送机器人动作；可保存审计与检查凭证 |
| `POST /api/tasks/{task_id}/resume` | 接受一个恢复操作 | 可能继续或重新执行已批准步骤 |
| `POST /api/tasks/{task_id}/cancel` | 进入取消生命周期 | 可能向下游发停止请求 |
| `GET /api/operations/{operation_id}` | 查询 resume/cancel 接受结果 | 否 |

保留 `POST /api/task_preflight` 作为新任务只读预检。恢复检查应有独立接口，因为已抓取任务不能再执行“新任务空手”门。

### 14.1 恢复检查响应示例

~~~json
{
  "task_id": "task-example",
  "state": "RECOVERY_REQUIRED",
  "state_revision": 27,
  "plan_revision": 1,
  "recovery_check_id": "check-example",
  "execution_state_known": true,
  "remote_active_command_id": null,
  "ready_for_resume": true,
  "requires_operator_confirmation": true,
  "proposed_action": "RETRY_STEP",
  "resume_step_id": "nav_relay2",
  "completed_steps_to_keep": ["nav_table2", "pick_cola"],
  "blockers": [],
  "observed_holding": {
    "value": "cola_can_1",
    "evidence_level": "hand_state_only"
  },
  "expires_in_sec": 10
}
~~~

恢复检查结果应有短有效期，并绑定 task revision、plan revision、资源代次和现场证据摘要。**检查有效期内也不能省略执行时再次核查**。

### 14.2 resume 请求与幂等

~~~json
{
  "operation_id": "resume-operation-example",
  "expected_revision": 27,
  "recovery_check_id": "check-example",
  "action": "RETRY_STEP",
  "step_id": "nav_relay2"
}
~~~

服务端规则：

1. 先按 operation_id 查已有操作：相同请求返回原结果，内容不同返回 409。
2. 验证操作者身份/权限；不能只相信请求体自报姓名。
3. 验证任务 revision、检查凭证和当前实际条件。
4. 在事务内比较 revision 并创建新的 attempt/领取恢复操作，两个并发请求最多一个成功。
5. 返回 202 与 operation_id/attempt_id/command_id，表示接受，不是动作成功。
6. 请求超时后调用 GET operation 查询；不换 operation_id 重发。
7. 工作线程实际执行前确认资源代次仍有效。

错误响应建议：400 请求不合法、403 权限不允许、404 任务不存在、409 版本/状态/幂等冲突、503 依赖不可确认。应用结构化 reason_code；不要依靠中文错误文本作为重试开关。

### 14.3 新任务准入

`publish_task` 也需要相同程度的幂等与并发准入，不能只给 resume 上锁：

- 同 task_id + 相同请求，返回已有记录；不同内容 409。
- 检查同机器人是否有未解决动作或被隔离资源。
- 第一次请求先持久创建任务再启动 worker。
- 不无条件清空所有 busy，不默默替换仍运行的任务。
- 任务正在 PLANNING 时同样占用其准入记录，防止两个 LLM 规划结束后同时执行。
- 查询类入口应明确识别只读能力，不能靠任意 LLM 自述绕过动作准入。

## 15. 取消与结束本轮

取消不是“让 Python coroutine 不再 await”：

1. 将任务设为 CANCELLING，停止派发新的步骤。
2. 根据记录找到所有仍可能执行的下游 commands。
3. 调用对应下游正式取消接口；若不支持，返回人工处理需求。
4. 查询原命令，等待终态、策略停止和资源归还证据。
5. 核实期间可能发生的业务效果（如手已经张开）。
6. 确认后才转 CANCELLED，并释放相关资源。
7. 无法确认时转/保持 RECOVERY_REQUIRED，继续标记 blocks_new_motion=true。

取消与成功同时到达必须按事务处理：保留实际已完成动作事实。整个任务是否取消取决于剩余工作，不能覆盖成功记录来制造“动作从未执行”。

物理支撑和手中物体的收尾不应通过通用“逆操作”自动补偿。比如 pick 成功后的取消不等于自动张手；需要业务/现场处理。

当前 `DreamClient.cancel()`、`VlaClient.cancel()` 已有调用方法，可复用。SSH 核验表明两侧现有 cancelled 状态都可能出现在停止证据不足时：导航先写 cancelled 再 lock；VLA 可根据 cancel_event 选择 cancelled。因此 Master 必须检查停止和所有权证据，不能仅等待 cancelled 字符串。下游修正点见第 17.2、17.3 节，Master API 和工作线程的统一取消流程仍需新增。

## 16. 网页与操作人员体验

### 16.1 网页状态

页面区分：

- 执行中；
- 连接中断，正在确认原任务；
- 待恢复：列出具体 blocker 与下一步建议；
- 恢复中：显示原 task_id、恢复步骤、新 attempt；
- 取消中：等待远端停止；
- 已完成 / hand-only 完成 / 已失败 / 已取消。

按钮建议：

- **检查恢复条件**：允许获取新事实，不自动执行；
- **继续原任务**：展示“继续跟踪”或“重试哪一步”，绑定恢复检查结果；
- **结束本轮**：走 cancel 生命周期；
- **新建任务**：资源未核清时禁用并说明原因。

不要提供无条件“标记成功”“清 busy”“跳过抓取依赖”。若需要人工补录效果，必须标识来源、时间、操作者、证据等级和下游状态修正流程，不伪装成传感器结果。

### 16.2 状态兼容

新增权威字段：

~~~json
{
  "schema_version": "brain/task-status/v2",
  "task_id": "task-example",
  "state": "RECOVERY_REQUIRED",
  "state_revision": 27,
  "active_step_id": "nav_relay2",
  "execution_active": false,
  "terminal": false,
  "has_failures": true,
  "blocks_new_motion": true,
  "can_resume": false,
  "completed_steps": 2,
  "blocked_steps": 3,
  "recovery": {"blockers": ["LOCALIZATION_NOT_APPROVED"]}
}
~~~

过渡期间旧字段建议：

- active：任务仍未关闭时 true；
- all_done：仅明确业务终态时 true，不是 worker 线程已返回就 true；
- failed：最终任务 FAILED 时 true；尝试失败另用 has_failures；
- completed：明确其统计“终结步骤”还是“成功步骤”，新增独立计数消除歧义；
- 未执行后续步骤展示 BLOCKED，不算物理动作失败；
- 原 reception_state 可以保留为兼容视图，从新存储派生。

后端与网页状态解析必须同步调整：网页应以 `state`、`terminal`、`blocks_new_motion` 等新字段判断执行与恢复状态，不能继续只依赖 active/all_done 推断可以发起新动作。过渡期间保留旧字段以便逐步上线。

### 16.3 网页刷新、重新连接与重复操作

- 网页刷新后按原 task_id 查询状态和事件，不重新调用 publish_task。
- HTTP 请求超时后按原 operation_id 查询结果，不新建恢复操作。
- 恢复按钮绑定任务版本和 recovery_check_id；过期页面必须重新检查。
- 多标签页同时操作由后端事务和幂等键保证最多一次接受，不能只靠前端禁用按钮。
- 页面重新连接时补拉遗漏事件；关闭页面或停止轮询不表示机器人任务已经取消。
- 本期操作入口统一为 8888 网页 / HTTP，其他入口的接入另行规划。

### 17.2 导航侧：命令恢复与停止确认

主文件：`DREAM/tools/g1_agent_navigation_service.py`。

#### 17.2.1 存储位置与启动顺序

现有 output_dir 随运行启动可能变化。恢复存储必须使用**稳定服务目录**，与每次 run 的图像、地图导出和诊断目录分开。

推荐增加轻量 command store 模块和独立 SQLite；若第一批仍沿用 JSON，也必须有单写者、revision、不可变命令历史和可靠迁移，不能只在构造函数读一个可能已被覆盖的文件。

拟议启动顺序：

~~~text
取得服务实例锁
 → 打开稳定命令存储
 → 校验 schema / 服务部署身份
 → 加载历史命令与结果
 → 将非终态命令标记 RECONCILING
 → 对照当前 9882 的原 command / plan / 执行状态
 → 生成可查询的状态视图
 → 最后写最新快照并开放新任务准入
~~~

- 启动恢复不能再次调用 set-agent-world-goal 或 execute-shadow-goal。
- 若 9882 也重启、原计划身份丢失，仅凭 pose 接近目标不能自动补写 succeeded。
- 不恢复旧 localization_approved=true。历史批准不能跨现场重启当作当前批准。
- 老数据导入先校验命令 ID、请求摘要、路线版本；损坏记录隔离保留。
- 启动后 GET 应能查询历史终态，包括用于 VLA 凭证的成功命令。
- 未解决命令和被未结束任务引用的结果禁止按 TTL 删除。终态保留策略要覆盖恢复窗口，并明确查询期限。
- 若只保留有限结果，过期后保留 tombstone（ID、摘要、曾执行/终态标识），不能把删除后的 404 当作“从未接收”。

#### 17.2.2 修正并发准入和幂等顺序

当前有 RLock，但完整请求预留没有覆盖所有窗口。建议：

1. 校验基本格式并计算摘要；
2. 在事务内查已存在的 command_id；同摘要返回原记录，不重复检查已经执行过的前置条件；
3. 不同摘要立即 409；
4. 检查未解决命令、资源代次及当前准入条件；
5. 同一事务创建完整 ACCEPTED 记录并占用资源；
6. 提交后启动唯一 worker。

同一 task 的某 leg 允许新 attempt 时，新 command_id 保留原 task/leg；旧 attempt 必须已可靠停止。成功历史不可因 retry 被覆盖。

#### 17.2.3 明确停止确认

将取消流程调整为：

~~~text
cancel requested
 → CANCELLING
 → 针对原 command 请求软件锁定/取消
 → 接收带 command 身份的锁定回执
 → 等待执行器 idle/goal cancelled、零指令及新鲜反馈满足停止合同
 → stop_confirmed=true
 → CANCELLED
~~~

需要同步检查 `g1_hybrid_localization_web_view.py::lock_navigation()` 及底层实际可提供的反馈字段：

- 增加请求身份/代次，防止旧 worker 的迟到 lock 影响新的任务；
- 明确 lock 是“请求已发布”还是“已满足停止条件”；
- stop 确认至少关联原命令、执行器状态、最新反馈时间和由导航组定义的稳定窗口；
- 有本体速度/运动状态数据时按已审核阈值确认；只有软件目标为零时，不能冒充实际物理停止；
- 反馈不足返回 UNKNOWN/UNCONFIRMED，不能强制 true；
- lock 失败或取消确认超时后仍保留资源隔离；活动命令指针清空不能使新任务自动通过；
- `_set_command()` 使用合法迁移和版本校验，避免 cancel/success/worker 错误互相覆盖；
- 进程 stop_event/退出路径不得在仍可能运动时无条件清 active 并开放后续任务。

动作执行失败仍然可以调用锁定保护，但应将“原失败原因”和“停止请求/确认结果”分开保存。

#### 17.2.4 保留导航自己的有限恢复

保留现有定位新鲜度等待、审批等待、Arm 就绪等待、已知路由约束。

Master 在这些状态下跟踪原 command，不新建导航 attempt。只有导航已明确失败且停止确认、定位重新符合要求，才由 Master 决定是否重试同一逻辑 leg。

建议结构化暴露 `can_accept_navigation_goal`、`standby_reason`、`localization_epoch`、`map_revision`。不要把 VLA 传回的 ready 当作另一份独立硬件证明，形成互相转述的健康状态。

### 17.3 VLA 侧：保留保护并增加受控恢复

主文件：`g1_brain_vla_bridge/bridge_service.py`。

#### 17.3.1 任务事实与当前执行状态分离

保留 current_state 的历史任务与请求摘要，新增以下信息：

- service_instance_id、state_revision；
- action_started（三态：true/false/unknown）；
- hook_instance_id、hook_pid、process_start_time、受管推理会话身份；
- hook_stopped、policy_stopped、action_publisher_stopped；
- hand_effect、holding、holding_certainty、evidence_level；
- handoff_id、relay_instance_id、owner、ownership_verified；
- unresolved_commands、blocks_new_motion。

PID 必须同时核对启动时间/可执行文件或进程组身份，防止 PID 复用。hook 退出不等于独立 tmux 策略进程退出。

当后台线程发生未知异常、停止证明不足或归还失败时：

- 保留 unresolved command 和隔离标志；
- 任务进入 RECOVERY_REQUIRED 或等价可表达状态；
- 可以记录 worker 已退出，但不把此事实转成“机器人空闲”；
- control/status 同时返回逻辑状态和实际核验结果；
- 不仅根据 _active_command_id 推导 policy_running=false；
- 不以 DREAM 返回 transport ready 覆盖本次失败留下的未解决资源状态。

#### 17.3.2 受控恢复接口（拟新增）

VLA 需要两个独立职责：

- `POST /v1/vla/tasks/{command_id}/recovery-check`：只读采集原 hook/策略/端口/holding 证据，返回阻塞项与 revision；
- `POST /v1/vla/tasks/{command_id}/resolve`：在版本、身份和证据满足后，核定旧尝试的终态/效果并解除对应隔离；**本接口不重做 pick/place**。

resolve 必须具有 operation_id 幂等、expected_revision、具体 command_id、允许的核定动作与证据引用；拒绝一个通用 `clear_recovery=true` 请求。

核定动作可以是：确认原动作未开始、补记已有成功证据、确认失败且停止、确认取消且资源已归还。原活动进程仍在时，resolve 不能将它清掉；需要先走真实取消。

重启恢复到的任务没有原 worker，旧 cancel_event 被置位并不会自动停止历史 tmux。新版需要根据持久身份查询/取消原执行器，无法确认则保持待恢复。

全局 recovery_required 应由所有 unresolved records 推导：只处理一个 command，不能顺便清除其他未解决记录。

#### 17.3.3 holding 与动作结果

当前 _holding 主要在完整成功时更新。抓取实际已闭手但随后归还失败，或 place 已放开但最终异常，都可能使缓存持有状态与现场不一致。

建议保存“动作效果已发生”的中间证据，不必等整条 hook 成功才记录；效果、停止和归还各自有状态。

- 不根据取消/失败自动写 holding=null；
- 不因 policy_stopped=true 推断物体已释放；
- hand-only 仍明确为手状态推定；
- 人工移物后的修正通过独立、经身份核验的事实更新，引用原任务与最新现场确认；
- 旧结果不能覆盖较新的物体事实 revision。

#### 17.3.4 取消与超时统一收尾

现有取消已尝试读 hook 返回并核查停止/归还，可以复用。需要修正：

- cancel_event=true 不足以产生 CANCELLED；停止/资源证据不足时转 RECOVERY_REQUIRED；
- ACTION_TIMEOUT 也应收集 hook 收尾输出和实际进程状态，不能直接丢弃恢复结果；
- SIGINT → 等待 → SIGTERM 之后继续验证目标进程/会话退出，不能仅依据 send signal 成功；
- 清 active 与释放资源分开；
- stdout/stderr 应持续消费并限制缓存，避免等待子进程退出期间管道写满；这是需要故障注入验证的潜在阻塞路径；
- 启动脚本替换 HTTP 服务前同时检查 unresolved 状态及动作会话，不只依赖可见进程名称。

### 17.4 Hook 与 relay：端口归还作为独立事务

#### 17.4.1 修复 hook 收尾覆盖范围

pick/place 的 acquire_action_port、信号处理、模型启动、停止和归还应进入统一管理范围。

拟议结构：

~~~python
# 设计伪代码；不直接运行。
handoff = prepare_handoff_identity(request)
install_signal_handlers()

try:
    acquire_or_reconcile_handoff(handoff)
    require_current_handoff_owner(handoff)
    start_and_track_action_processes()
    collect_action_effect_evidence()
finally:
    stop_report = stop_and_verify_owned_action_processes()
    if stop_report.action_publishers_stopped:
        release_report = request_release_with_hand_policy(handoff)
    else:
        release_report = quarantine_without_reopening_navigation(handoff)
    persist_separate_effect_stop_release_reports()
~~~

- acquire 超时可能发生在 relay 已释放之后，不能仅按本地 acquired=false 忽略收尾；用 handoff_id 查询原事务。
- stop_stack 返回码必须检查，且以进程/会话最终状态佐证。
- 一个 cleanup 动作失败不应阻断剩余必要核查；分别捕获、记录收尾错误。
- 确认 VLA 动作发布者停止前，不让导航重新占用出口。
- 无法完成归还时明确留下隔离，不打印 navigation_port_ready=true。
- 不使用统一默认的 policy_stopped=true 结果模板掩盖真实状态。

#### 17.4.2 带身份的端口交接协议

现有 ROS Bool 信号没有 command 身份。建议采用自定义 ROS message/service，或等价的内部请求/响应协议；第一版保持传输栈不变，优先实现版本化消息。

示例请求（拟议 `fq/action-handoff/v2`）：

~~~json
{
  "protocol": "fq/action-handoff/v2",
  "operation": "ACQUIRE",
  "request_id": "request-example",
  "handoff_id": "handoff-example",
  "task_id": "task-example",
  "command_id": "vla-pick-example",
  "attempt_id": "attempt-example",
  "expected_relay_instance_id": "relay-instance-example",
  "expected_owner_epoch": 12
}
~~~

应答需要回传全部身份、实际 relay_instance_id、新 owner_epoch、状态、资源核查结果与失败原因。请求者只接受与本轮身份完全匹配的应答。

推荐 relay 状态：

~~~text
NAVIGATION_READY
 → RELEASING
 → VLA_OWNED
 → RESTORING
 → NAVIGATION_READY

任意不确定状态 → QUARANTINED
relay 重启 → RECONCILING，而非直接假定 NAVIGATION_READY
~~~

要求：

- 相同 request_id/相同内容返回原结果；内容不同拒绝；
- acquire/release 可按 handoff_id 查询原结果，解决 ACK 丢失；
- ownership_epoch 单调递增，旧命令/旧应答无权改变新代次状态；
- 串行化 socket 绑定与交接操作，禁止并发 acquire 交叉；
- 旧实例 ACK 与新实例 ACK 必须可区分；
- 未解决交接不得 TTL 自动解除，也不能超时自动回导航；
- RELEASE 必须验证 VLA publisher 已停止，并确认正确 relay 恢复出口；
- 恢复应包含匹配代次的新鲜转发证据。端到端 NX 接收确认若暂不支持，明确 capability=false，不声称仅有 ESTAB 就证明完整链路正常。

#### 17.4.3 分离手部策略与端口所有权

现有 `on_task_stopped()` 无条件置 `carry_hold_closed=true`，要改为显式 `hand_policy`，而不是依赖完成 topic 名称：

| 动作状态 | 归还时手部策略 |
| --- | --- |
| pick 成功且有一致持有证据 | 显式 carry_closed，并绑定该效果证据 |
| place 成功且释放证据通过 | 显式 cleared/open 策略 |
| 取消/失败且持有仍未知 | preserve_last，不改变手部目标；隔离后续物理导航 |
| 开始前失败、已确认空手 | 可选择空手策略，但不能通过 task_stopped 自动握拳 |
| relay 重启 | 从持久事实核查并建立新策略，不以默认 false 推断空手 |

preserve_last 的含义必须落实到动作数据层：缓存并复用最后核验的手部字段，或使用已验证的“保持目标”机制；不能简单停止 overlay，让上游默认零值意外张手。缓存不存在或无法核验时，不恢复动作转发。

取消与归还只负责资源收尾，不能顺便握拳、松手或修改物体事实。闭手保持会影响物理机器人，必须跟随具体动作效果与现场策略。

#### 17.4.4 过渡部署

- v1 Bool 与 v2 事务协议不能同时驱动同一 relay 状态机。
- 新旧模式通过配置显式互斥；没有完成 v2 验收前，不宣称具有自动跨重启交接恢复。
- 若暂时保留旧 Bool，仅支持核清无并发/无旧事务的人工恢复，禁用自动交接重试。
- 抓取、放置、失败和取消的手部策略都必须有独立测试，不能仅测成功闭环。

### 17.6 结合实际接口后的版本兼容

- 既有 `fq/reception-lan/v1` 的命令查询与成功结果校验继续可用。
- 大脑 step/attempt 可先保存在本地，通过 command_id 关联下游；但不能因此假定下游已经支持重试/重启。
- 新的取消中、隔离、恢复核定字段和状态需要协商版本或 capability，不能让旧客户端看到它不理解的状态后默认成功。
- VLA 处于 recovery_required 时，相同 ID 的 POST 当前也会被保护拦住；GET 原命令仍是恢复起点。
- 两侧都必须先持久接受并去重，再执行动作，才允许使用持久幂等重投。
- 旧任务使用其原协议/路线/证据策略；恢复时如需升级合同，必须核清旧动作并记录显式迁移，不能原地改 payload 摘要。
- 缺失 service instance / persisted command / stop evidence 时，降级为人工核查；不是只看端口可达就继续。

### 18.5 将实施拆成可独立评审的变更包

| 变更包 | 内容 | 依赖 | 不具备时的限制 |
| --- | --- | --- | --- |
| BRAIN-BASE | busy/身份/等待/默认成功修正 | 大脑 + Slaver 协议同步 | 尚无自动恢复，仅能正确报告中断 |
| NAV-STORE | 稳定命令存储、启动恢复、去重原子性、门段历史 | 导航当前合同 | 不支持导航服务重启后的原任务续跑 |
| NAV-STOP | 取消中、针对原命令的锁定与停止确认 | 执行/反馈接口能力 | 只能保持待恢复，不能凭 cancelled 放行 |
| VLA-RECOVERY | unresolved 持久化、真实状态核查、受控 resolve、hook 收尾 | VLA 进程身份与停止核验 | 不能自动解除重启保护 |
| HANDOFF-V2 | 有身份的 acquire/release、owner epoch、hand_policy | VLA hook + relay 同步 | 保持旧协议人工模式，禁用自动交接重试 |

每个变更包只在其支持的能力通过测试后声明 capability=true；不能用一项 `recovery_supported=true` 掩盖仍缺失的停止或持久化能力。

## 20. 关键伪代码

### 20.1 调度一个步骤

~~~python
# 设计伪代码：强调状态边界，不可直接运行。
async def execute_step(task_id, step_id):
    task = store.load_task(task_id)
    ensure_task_owns_robot(task)
    ensure_no_unresolved_attempt(task.robot_id)
    facts = await collect_current_preconditions(task, step_id)
    require_preconditions(step_id, facts)

    attempt = store.prepare_attempt_atomically(
        task_id=task_id,
        step_id=step_id,
        expected_revision=task.state_revision,
        immutable_command_id=new_command_id(),
        facts=facts,
    )

    # 必须先落盘进入 DISPATCHING，再调用外部执行器。
    store.mark_dispatching(attempt)
    try:
        accepted = await executor.submit(attempt)
        validate_identity(accepted, attempt)
        store.record_accepted(attempt, accepted)
        result = await executor.wait_original_command(attempt, deadline=attempt.deadline)
    except DeliveryOrObservationUncertain as error:
        store.mark_unknown_and_quarantine(attempt, error)
        return await recovery.reconcile_original(attempt)

    # 即使返回 failed，也必须记录原始结果和是否可靠停止。
    facts = await executor.collect_postconditions(attempt, result)
    decision = verifier.evaluate(attempt, result, facts)
    store.commit_result_evidence_and_transition(attempt, decision)
~~~

### 20.2 核查原任务

~~~python
async def reconcile_original(attempt):
    remote = await executor.lookup(attempt.command_id)

    if remote.record_missing:
        # 404 可能意味着记录丢失/过期，而非未执行。
        return require_recovery("REMOTE_RECORD_MISSING")

    require_identity_and_digest_match(remote, attempt)

    if remote.running:
        return attach_status_tracking_to_same_attempt(attempt)

    if remote.succeeded:
        evidence = await verify_original_result_and_current_conditions(remote)
        return commit_verified_result_once(attempt, evidence)

    if remote.failed_or_cancelled and remote.stop_confirmed:
        return build_recovery_proposal(attempt, remote)

    return require_recovery("REMOTE_STOP_OR_EFFECT_UNKNOWN")
~~~

### 20.3 续跑与新任务不同

~~~python
async def resume(task_id, operation_id, expected_revision, check_id):
    # 重复的相同请求先返回原操作，不能因任务 revision 已变化而再执行一次。
    existing = store.find_operation(operation_id)
    if existing:
        return require_same_request_and_return(existing)

    report = await recovery.revalidate(task_id, check_id)
    if not report.ready:
        return reject_with_blockers(report)

    # 单事务校验 revision + 所有权 + 重试预算，并创建恢复操作。
    operation = store.claim_resume_once(
        task_id=task_id,
        operation_id=operation_id,
        expected_revision=expected_revision,
        decision=report.decision,
    )
    schedule_existing_task(operation)
    return accepted_operation(operation)
~~~

以上所有 query、wait 都要有自己的预算；伪代码中的 revalidate 之后、真正调用远端之前仍需确保执行权没有被取消/新代次替换。下游也要保留最后一层前置条件检查。

| 阶段 | 内容 | 交付与进入下一阶段条件 |
| --- | --- | --- |

| C2：VLA 恢复基础 | VLA-RECOVERY | 原任务、真实进程、持有和未解决资源可核查，恢复不靠重跑 worker |
| C3：动作交接基础 | HANDOFF-V2 | ACK 绑定本轮事务，relay 重启核查，归还不隐式握拳/松手 |
| D：大脑持久步骤与人工续跑 | BRAIN-RESUME：TaskStore、operation、reception step runner、网页 | 下游能力检查通过；pick 后导航失败可续且不重抓，跨重启仅在已支持范围内开放 |
| E：通用任务与网页适配 | 通用步骤依赖、复合动作子检查点、v2 展示与重新连接 | 通用任务和固定接待共用恢复机制，网页正确跟踪原任务 |
| F：有限自动恢复 | AUTO-RECOVERY：查询重连、明确未开始重试、导航错误白名单 | 故障注入证明预算有界、无重复动作；未知资源不自动释放 |
| G：LLM 局部重规划 | 结构化事实、计划差异审核、计划版本 | LLM 无法跳过依赖、降证据或重复副作用 |

开发顺序是技术依赖顺序，不是工期承诺。先保持单机器人单动作任务；完成这些验收后，再评估多机器人并行和资源级依赖图。

C1/C2/C3 可以分别开发、离线验证，但涉及同一端口的真实部署必须由同一维护流程协调。阶段 D 的某项续跑能力必须等待其依赖的下游验证通过，不能仅因网页按钮已经做好就开放。

不建议第一版同时升级模型、调整低层控制时限和修改导航路径，否则无法判断中断恢复机制本身是否正确。

| T40 | VLA 重启后残留独立推理 tmux，没有原 worker | 能查询实际执行并按身份取消/核定 | 仅 set cancel_event 不可宣告已取消 |
| T41 | VLA cancel_event=true，但 hook 未证明停止/归还 | RECOVERY_REQUIRED + blocks_new_motion | 不把 cancelled 当作资源可用 |
| T42 | VLA 超时，hook 已部分收尾并输出证据 | 收集停止、效果、归还的独立结果 | 不丢失部分证据，不固定写 policy_stopped=true |
| T43 | VLA 多个未解决 command，只 resolve 一个 | 其他记录继续阻挡新动作 | 不全局清 recovery_required |
| T44 | acquire 已使 relay 释放，但 ACK 丢失 | 按 handoff_id 查询原事务 | 不重复释放，不因 acquired=false 绕过收尾 |
| T45 | acquire 后 monitor/PTY/子进程初始化失败 | 收尾覆盖该窗口并明确结果 | 无孤立释放端口、无假 ready |
| T46 | stop_stack 失败或 TERM 未使动作进程退出 | 记录停止未知并隔离资源 | 不直接归还导航，不假报 policy_stopped=true |
| T47 | 旧 handoff ACK、重复 RELEASE、新旧 relay 实例交错 | 只接受当前事务和代次 | 不使当前所有者被旧消息覆盖 |
| T48 | relay 在持有物体阶段重启 | RECONCILING，恢复手部/owner 后才转发 | 不因默认 carry=false 导致上游张手目标透传 |
| T49 | pick 失败/取消后归还 5556 | 显式 preserve_last 或待核查策略 | 不通过 task_stopped 自动握拳 |
| T50 | place 已张手，但最后归还失败 | 保存已释放效果与归还失败，待恢复 | 不保留错误的确定 holding 或重新放置 |
| T51 | DREAM 有 ESTAB，实际 relay 未正确出流 / NX 未确认 | 分层状态分别报告未知/失败 | 互相转述 ready 不冒充独立端到端证据 |
| T52 | VLA 引用别的 task/旧定位代次的成功导航凭证 | 拒绝不适用凭证 | 不靠历史 command succeeded 单独放行新操作 |

T01–T32 覆盖大脑与整体调度；T33–T52 是本次 SSH 实查后的下游专项补充。另对 backend stdout/stderr 大量输出做进程级注入，确认日志管道不会使 hook/HTTP 线程互相等待。

### 22.1 测试实施方式

- 单元层：假时钟、事件乱序、事务冲突、错误分类和条件检查。
- 进程层：fake Slaver/fake HTTP 服务，真正退出进程和丢响应，检验持久化窗口。
- 传输层：消息重复、丢失、延迟、断线重连；记录真实外部调用次数。
- 集成层：运行在临时目录和独立 Redis database/命名空间，避免污染生产。
- 现场层：先只读恢复检查，再在已确认现场条件下分段验收；不在危险动作中随意断电测试。

最重要的自动化指标是：**同一个尝试的副作用调用最多一次，未知状态不触发新动作，可恢复时能保留已完成步骤继续。** 如果下游缺乏持久去重，必须在测试报告中标明无法保证的窗口，而不是宣称物理 exactly-once。

## 23. 观测指标与日志

每条执行/恢复事件应包含：

`task_id, step_id, attempt_id, command_id, operation_id, worker_session_id, ownership_epoch, state_revision, error_code, execution_certainty, timestamp`。

日志与页面保留原始下游错误。例如 NX feedback stale 应直观显示，而不是只有“大脑成功证据不完整”。

建议统计：

- 无响应等待超限次数及最终处理状态；
- stale/duplicate result 拒绝次数；
- UNKNOWN 命令的查明率与查明时间；
- 人工续跑次数、成功率、恢复所用步骤数；
- 每类动作的真实尝试数、查询重试数；
- 重复副作用事件数（验收应为 0）；
- 恢复检查过期/版本冲突次数；
- 因 holding/map/ownership 冲突拒绝的次数；
- 本地终态与远端终态不一致次数；
- 持久化失败和检查点落盘耗时。

避免把高频完整图像或用户凭证写进日志。生产数据库、现场证据、用户操作记录和持有状态均应留在私有 runtime 目录。

## 24. 迁移、部署与回退

### 24.1 旧状态迁移

1. 仅在已确认无活动真机动作的维护窗口进行首次迁移。
2. 备份 current_task.json、相关事件及配置；保留源数据与 hash。
3. 将旧 task/command 记录按 legacy 协议导入，缺失身份/停止证据保持 unknown。
4. 旧 FAILED 若远端停止未确认，也要保留 unresolved 标记。
5. 旧 RECOVERY_REQUIRED 导入非终态；不能因名称出现在旧 terminal 集合里就归档。
6. 旧图像和 holding 仅作为历史证据，不能覆盖实时现场状态。
7. 迁移脚本幂等，同一旧记录重复导入不产生新的执行尝试。
8. 校验完成后切换权威存储，旧 JSON 只读保留。

导航侧额外要求：在第一次启动新版 AgentBridge 前备份旧 output_dir 的 state_latest.json 和 command_events.jsonl，禁止让旧初始化流程先写空 commands 覆盖唯一迁移来源。按既有请求摘要和目标验证导入，不将只存在于大脑的自然语言成功描述伪造为导航权威结果。

VLA 侧额外要求：保留现有请求/摘要/holding 与 service.lock 机制。对“终态但停止/归还 false”的旧记录建立 unresolved resource 项；对没有原 worker 的历史活动任务，只查询和核查，不能重建线程直接执行旧动作。

### 24.2 渐进上线

- 新代码先用 feature flag 关闭实际恢复。
- shadow 阶段根据日志/假服务生成恢复建议，但不驱动现场动作。
- 打开“只读恢复检查”和网页状态。
- 人工确认续跑验证通过后，再逐类打开自动策略。
- 固定接待和通用任务分别灰度；Master、Deploy 与网页的状态协议同步发布。
- 以固定源码版本和服务 capability 记录每次实验环境。

三端上线应先关闭新动作准入，完成旧任务核清，再部署导航恢复、VLA 恢复和新交接协议；原 Bool 模式与 v2 必须互斥。基础测试通过后再开启大脑 resume。网络配置加载、代理绕过和现有物理启动确认属于已核验基线，恢复重构不能将它们回退成旧脚本。

### 24.3 回退原则

- 回退前暂停新任务准入，核清或取消所有正在运行/未知尝试。
- 数据库不可简单清空，不能还原老 JSON 后丢弃已执行事实。
- 旧程序无法理解新 schema 时不允许直接启动它去接管未完成任务。
- 可回退到仅诊断/只读模式；仍保留 unresolved resource 记录。
- 不把“关闭新功能开关”当作机器人动作已经停止。

- handoff v2 存在未解决事务时，不直接切换回旧 Bool relay；先核清端口、实际发布者和最后手部目标，再按维护流程切换。
- 导航新存储迁移后，不能回退到启动即清空命令视图的旧实现并继续原任务；旧版仅可在无未解决任务的新维护周期内使用。

## 25. 第一版完成标准

第一版完成应至少满足：

- [ ] Slaver 或网络中断后不会无限等待。
- [ ] 没有完整终态证据时不默认成功。
- [ ] 旧结果、重复结果不改变当前执行尝试或 busy。
- [ ] 新任务不能覆盖仍有未知动作的旧任务。
- [ ] 每次外部命令在发出前已有持久身份和发送意图。
- [ ] 原命令结果找回后，不重复已完成动作。
- [ ] pick 后导航失败可从导航步骤恢复，且保留持有证据等级。
- [ ] resume 按 operation_id 幂等，按 revision 防并发。
- [ ] 取消请求与实际停止被明确区分。
- [ ] Master/Slaver 重启后保留未解决任务和重试预算。
- [ ] 网页正确显示执行中、待恢复、取消中与终态。
- [ ] 网页刷新或重新连接后继续跟踪原任务，不重复提交，且不把 RECOVERY_REQUIRED 视为可开始新动作的空闲状态。
- [ ] 旧状态可审计迁移，回退不丢失物理动作历史。
- [ ] 故障注入测试中未发生重复抓取/放置或依赖未满足的后续动作。

两侧实查后增加的必达项：

- [ ] 导航重启可查询旧成功命令，门段前置记录不会因更换 output_dir 丢失。
- [ ] 导航取消区分软件锁请求与实际停止确认，旧命令不能锁定新任务。
- [ ] VLA 重启后能核查无 worker 的旧执行，受控 resolve 不执行新的抓取/放置。
- [ ] VLA 活动 ID 清空不自动清除 unresolved 或伪装 policy_running=false。
- [ ] 两个 hook 的 acquire、执行和 cleanup 全生命周期均在可恢复范围内。
- [ ] 5556 应答绑定 handoff/command/instance/epoch，重复和迟到信号不改变新事务。
- [ ] 归还动作端口不隐式改变手部目标；relay 重启先核查而非使用默认 carry 状态。
- [ ] 两侧 capability 如实声明，端口/连接就绪不冒充 NX 端到端确认。

在此基础上，再加入导航白名单自动恢复和 LLM 局部重规划。优化的结果应是“知道停在哪里、知道为什么停、核实后能继续”，而不是让每个错误都自动跳过。
