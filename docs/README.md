## 文档书写与更新规范

### 1. 一类事实只保留一份主文档

- 全局拓扑、职责和执行链路：更新 `架构说明_三端架构.md`；
- 某一端的字段、接口、状态和错误码：更新对应的 `接口说明_*`；
- 当前可执行的启动、预检、操作和收工步骤：更新 `联调说明_*`；
- 尚未落地或待评审的设计：统一更新 `规划说明_具身大脑重构.md`，不得混入当前能力，不另开专项规划；
- 已真实发生的问题：新增 `案例排障_YYYYMMDD_问题简述.md`；
- 不再新增“最终版”“当前版”“对齐回执”“决策确认”等平行文档。

修改前先查找已有主文档。能更新原文就不新建同主题文件。

### 2. 文件命名

```text
架构说明_主题.md
接口说明_端或模块.md
联调说明_场景.md
规划说明_具身大脑重构.md（唯一规划入口）
案例排障_YYYYMMDD_问题简述.md
```

日期使用问题实际发生日期；未知时明确写“日期待确认”，不要用文档创建日期冒充。

### 3. 当前事实、推断和规划必须分开

- **已实现**：必须能由当前代码、配置、接口响应或现场验证支撑；
- **已验证**：写清验证日期、范围和证据边界；
- **推断**：明确写“高可信原因”“尚未证明唯一根因”等限制；
- **规划**：明确标注“待评审 / 未实施 / 部分落地”，不得写成现有接口；
- 代码和现场行为已经变化时，及时更新主文档，不能保留冲突口径让读者自行判断。

事实优先级：

```text
当前运行代码与配置
→ 当前接口响应和现场验证
→ 架构 / 接口 / 联调说明
→ 案例排障
→ 规划说明
```

历史案例只证明当时发生过什么，不自动代表当前仍有同一问题。

### 4. 什么变化要更新哪份文档

- 大脑、导航或 VLA 对外接口变化：更新对应 `接口说明_*`；
- 三端职责、调用方向、部署关系或主流程变化：同时更新 `架构说明_三端架构.md`；
- 启动命令、端口、人工闸门或现场顺序变化：更新对应 `联调说明_*`；
- 已落地规划：把结果写入架构/接口/联调主文档，并在规划文档顶部标明已落地范围；
- 新故障完成排查：新增案例排障；通用结论同步回接口或联调主文档；
- 文件改名或删除：必须更新仓库内所有引用，不保留失效链接。

### 5. 内容要求

每份正文开头至少说明：

- 适用范围；
- 当前状态或更新时间；
- 哪些内容已实现，哪些尚未实现；
- 与其他主文档冲突时以哪份为准。

写操作步骤时必须包含前置条件、命令、成功判断和失败出口。涉及真机动作时必须保留安全门、人工批准和证据边界，不能只写“执行成功”。

### 6. 隐私与公开发布

- 不写真实姓名、个人缩写账号、密码、Token、密钥或个人 home 目录；
- SSH 使用角色别名，如 `dream`、`gpu4090`；
- 部署路径使用 `<DREAM_ROOT>`、`<VLA_PROJECT_ROOT>` 等占位符；
- 示例配置使用环境变量，不复制真实 `.env`；
- 内网 IP 仅在确有联调需要时保留，不附带个人身份信息。

### 7. AI 修改文档前必须执行

1. 先读项目根 `README.md` 和本目录索引；
2. 再读当前问题相关的架构、接口、联调或案例文档；
3. 对照当前代码和配置，不能只依据旧文档改写；
4. 不把规划内容写成已实现，不把单次日志推断写成唯一根因；
5. 优先更新已有主文档，避免制造重复版本；
6. 修改后搜索旧文件名、旧链接、旧地址和冲突表述；
7. 检查 Markdown 链接与格式，并在交付说明中列出合并、删除和仍未确认的内容。
