## 维护规则

### 内容放在哪里

| 变化 | 更新位置 |
| --- | --- |
| 功能、字段、配置、操作或错误出口变化 | 直接修正对应接口说明的当前行为 |
| 实测、故障排查或复验产生证据 | 更新对应模块联调中的验证项／问题，注明真实日期、版本、环境及证据 |
| 职责、依赖、状态权威、恢复或交接机制变化 | 更新系统架构；关联接口和模块验证条目 |
| 大体积原始日志、逐帧轨迹、全部模型输出或视频 | 留在 `data/`、`logs/` 或独立实验目录；用于排障的命令、关键回包、参数、方法和必要对照表仍写入正文 |

一类事实只维护一处。模型配置不复制到多张“当前配置”表，失败也不能因另一个场景成功而消失。源码变化、实际实例重载和远端部署是不同事实；文档整理不授权重启或动作。

### 文件名与新增条件

```text
接口说明_端或模块.md
多端联调_模块.md
架构设计_系统架构与演进.md
```

- 联调文件名不含日期、轮次、服务器名或某次测试结果；日期写在具体证据条目中。
- 同模块的新一轮测试更新原条目，不新增当天文件，也不在文末持续追加“第 N 轮”。
- 仅当新增独立模块／验证职责，且现有模块无法清晰承载时，新增文档并同步索引与引用。不要为一次优化或单个故障新建长期文档。
- 不另建“总结版”“最终版”“联调说明”等平行正文，也不靠新增每日归档目录继续同样的增长方式。

### 联调正文如何持续更新

每个模块维护验证概览／矩阵、排障章节导航、详细问题与复验、待验证项和来源。概览用于快速判断；详细章节必须足以直接参考排查，不能要求读者先翻 Git 或打开原始日志才能知道怎么复现、为什么失败、改过什么。日期与版本标在相关章节内。

1. **更新验证项。**注明证据日期、代码／模型版本、执行环境、输入规格与成功标准。重复测量更新该项的范围和证据引用，不堆积相同结论。
2. **记录问题闭环。**保留首次发现、确认的原因或仍待核实的假设、修复与复验依据。未修复、未复验及只在隔离副本修复须明确区分。
3. **处理旧结论。**不同条件下的结果并列说明，保留各自版本、输入、参数和判定条件。同条件下被替代的结论要说明修复与复验；仍可用于排障的方法、错误原文、根因依据和关键失败回合继续保留在正文。Git 保存版本历史，不承担日常排障正文的职责。
4. **按信息价值去重。**合并真正重复的介绍和过程，保留独有的参数、命令、回包、失败与条件差异。已解决问题也需保留定位方法及修复为什么有效；大段原始采样可移到证据目录。不得以行数减少或只剩摘要作为整理成果。
5. **区分验证层次。**代码可调用、HTTP 成功、schema 合格、模型语义正确、Runtime 完成与物理动作通过不能互相替代。原始任务／命令身份及失败详情必须能追溯。

文档合并时逐项核对：环境／版本、输入与参数、复现步骤、关键命令和错误、根因依据、修复、复验结果、未通过范围及证据位置。原文未记录的项目注明未记录，不猜测补齐。跨模块拆分需提供直达实际正文的链接，原任务／命令身份不丢失。

证据文件保存完整逐次数据；关键任务、步骤、尝试、原命令、参数、回包、失败、耗时和判定依据在正文直接可见。凭据和大体积原始数据不入源码，`data/memory` 的运行时经验不属于 Docs。证据存于其他机器或忽略提交目录时注明位置与可用性，不能假定克隆仓库即包含它们。

### 核准与收尾

改动前检查工作区并保留他人修改。按代码、生效配置及有日期的证据核准内容；不能把整理日期当实验日期，或把引用的历史回归写成本次运行。

改动后运行：

```bash
venv/core/bin/python scripts/check_docs.py
git diff --check
```

检查模块索引、禁止的日期文件名、相对链接、章节锚点及迁移前 Git 原文是否可读取。链接检查之外，还须对照来源核查正文内容完整性；链接全绿不能证明没有误删信息。跨模块引用定位到实际方法或故障章节，旧文件名仅保留在明确的历史来源引用中。

代码变更另按范围运行有意义的测试；完整离线入口为 `venv/core/bin/python scripts/run_tests.py`。文档维护不需要启动真机。提交前核对暂存范围，交付说明区分本次实际验证、引用的旧证据和剩余限制。
