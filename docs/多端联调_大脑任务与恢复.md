## 问题与闭环

### 查询、重试和停止的边界

2026-08-31 的抓取后导航控制未恢复，以及 2026-09-17 的导航启动人工闸门超时，分别保留端口／本体接管和现场启动事实。[B1](#e-b1)、[B2](#e-b2) 中的分析是当时线索，不是所有控制器版本通用的已确认根因。

后续控制机制以原任务、步骤、尝试和命令身份查询与核验。大脑任务结束、下游命令结束与机器人停止分开记录；网络异常、超时、查不到命令不能推断动作未执行。实际控制器实例、代次和接管凭证仍需相应执行端证据。

### 异常建议与失败后推进

2026-10-15 派发延迟记录中的一段等待约 94 秒。修复针对模型建议同步阻塞，增加阶段日志并允许原 Runtime 继续处理控制请求；建议依然绑定任务、命令和账本版本，迟到或失效建议不能推进新状态。

同日操控明确拒绝的修复使用原拒绝回包，而非查询一个未被接收的命令。它没有放宽未知命令处理，也不改变成功门限。以后复验这两项时，应分别覆盖明确拒绝、受理后失联、迟到结果和新旧尝试混淆。

## 执行异常后的受限恢复方案

2026-10-21，用户确认在原执行架构内补充异常后的 LLM 处理能力。本次修改为第一版受限实现：
只读刷新执行端状态与场景，再让 LLM 提议保留所有未完成步骤的执行顺序；人工确认后由原 Runtime
重新核查并应用。SOP 顺序、目标与动作参数不变，通用任务仅支持独立物体抓放顺序调整。
具体合同、策略绑定、60 秒读取时效与次数上限统一见[大脑接口第 1.1.3 节](接口说明_大脑%20Brain.md#113-执行异常后的受限恢复方案)。

**实际验证。** 使用临时账本、脚本执行替身和本机测试端口，未连接机器人、未切换现场环境。
新增回归覆盖：读取现场不产生物理命令；方案接受后保留原失败与任务身份；通用两组抓放可重排；
SOP 路线重排、遗漏／重复步骤、任意坐标字段、抓放依赖冲突均拒绝；完成前缀保持。
原动作结果未知时，必须先查询原命令；查询确认失败后可提议方案，但保留原 UNKNOWN 回包。
确认时原结果变为成功、停止／资源不明或下游禁止重试均不得重发。
还覆盖过期观测、预算耗尽、读取失败、旧任务未绑定策略、重复确认、取消期间的迟到读取／查询、
确认后重启不重放，以及前端方案顺序、文本转义和控制回包未知时禁用执行按钮。
SIMPLE 通用 `/v1/scene` 为场景模板，测试确认不会因此允许重置物理回合。

首轮完整回归只发现一个界面断言仍期待“人工继续触发”，与本次包含恢复方案的“人工确认触发”不符；
修正断言后最终运行 `venv/core/bin/python scripts/run_tests.py`，**618 项测试（约 86.77 秒）及
27 项 DREAM 自检全部通过**。此前失败输出保留在证据目录，不冒充最终通过。文档与差异格式检查另行执行。

**真实模型＋替身闭环。** 使用当前配置的 `deepseek-chat`，独立探测任务 ID 为 `recovery-live-model`，
初始计划在测试中固定为 `STEP_1 抓取 milk_1 → STEP_2 放置 milk_1 → STEP_3 抓取 milk_2 → STEP_4 放置 milk_2`。
用户目标为“把 milk_1 和 milk_2 都放到 milk_area，顺序不限”。替身设定 milk_2 未搬走时，
抓取 milk_1 明确失败且停止、资源释放。该障碍是脚本条件，不是真实碰撞检测或物理场景。

| 环节 | 实际结果 |
| --- | --- |
| 首次执行 | STEP_1 失败，记录“milk_2 挡住了 milk_1 的取物入口，已停止且未抓住” |
| 第一次 LLM 决策 | `observe_scene`，说明没有新现场证据，应先读取状态 |
| 脚本模拟人工确认 | 只读获取两物体未持有状态和目标区；没有新增抓放 |
| 第二次 LLM 决策 | `revise_plan`，提出 `STEP_3 → STEP_4 → STEP_1 → STEP_2`，引用本次 observation_id |

| 效果核验 | 原 SimAdapter 根据替身物体位置与持物字段核验，两个物体均在目标区且未持有，任务 succeeded |

分别保留；初始计划由测试给定，本轮只验证真实模型的异常后选择与受限修订，不宣称初始规划或真实物理任务通过。

### 1. 现象

机器人成功导航到 table2 并完成 VLA 抓取后，系统记录 5556 已归还导航，但进入 relay2 时机器人没有正常完成转向。

### 2. 已确认事实

- table2 导航成功，最终位置误差 0.082m；
- table2 最终朝向残差 7.52°，朝向调整达到 15 秒限时；
- 大脑和 VLA 均记录抓取成功，但证据等级是 `hand_state_only`，照片验证关闭；
- VLA 键盘日志末尾发送 `k`，运行语义对应 STOP；
- relay 日志记录重新绑定及 `navigation_ownership_restored`；
- NX 日志出现 `STOP → safe hold` 锁定，之后仍收到大量 Token；
- 较晚才出现显式 START 解除保持；
- 当时代码中，relay 归还只恢复帧转发；导航 Token 控制器只在启动阶段发送 START；ROS Arm 不负责解除 NX 的 safe hold。

<a id="e-b1-s3"></a>

### 3. 排查判断

原流程错误地把以下状态视为同一件事：

```text
VLA 策略已停止
≠ 5556 出口已归还
≠ NX 已解除 safe hold
≠ NX 已采用导航输入
≠ 导航动作已经成功
```

5556 重新监听和 TCP 恢复只能证明传输出口归还，不能证明 NX 已解除 STOP 后的保持，也不能证明导航输入已被控制器采用。

<a id="e-b1-s4"></a>

### 4. 高可信原因

VLA 收尾发送 STOP 后，NX 进入 safe hold。relay 随后恢复 5556 转发，但缺少一次具备事务身份、可查询结果的受控接管过程，因此大脑和导航在 NX 尚未真正恢复导航控制时开始 relay2。

这是已确认的控制接管协议缺口，也是本轮故障的高可信原因。

当前证据仍有边界：

- NX 历史日志缺少逐行时间与任务身份；
- 排查时看到的源码不完全等于故障当时运行的二进制；
- Token、定位和姿态问题尚未全部排除；
- 因此不能将该协议缺口表述为已现场复现的唯一根因。

<a id="e-b1-s5"></a>

### 5. 当时不应采用的临时处理

- 不能只把 `navigation_port_ready=true` 当作 NX 已接管；
- 不能只检查 5556 端口或 TCP ESTAB；
- 不能删除 VLA 收尾的 STOP 来绕过安全保持；
- 不能循环补发裸 START，较新的急停或保护可能被错误解除；
- 不能简单延长导航无进展超时；
- 抓取效果已产生时不能重新执行 pick，只能修复原交接。

<a id="e-b1-s6"></a>

### 6. 修复方向

修复尚未完整实施，目标是把以下证据分开记录和核验：

1. VLA 动作效果已经产生；
2. VLA 发布者已经停止；
3. 5556 唯一出口已经切换；
4. 导航中性输入已经准备；
5. NX 已受控解除本轮可恢复的 safe hold；
6. NX 已实际采用本轮导航输入；
7. 大脑取得与原任务、命令和控制器实例一致的接管凭证后，才允许提交 relay2。

控制接管未确认时，relay2 调用次数必须为 0。交接失败只修复原 handoff，不重复抓取。

当前有效约束和真机验收要求见 [控制交接与后续验收](架构设计_系统架构与演进.md#3-后续演进)。旧专项接口草案已退出，历史事故证据保留。

## 站立后后续服务未启动：人工闸门超时

证据日期：2026-09-17。本节保留对应条件下的完整排查与复验内容；后续变化以文首验证概览及相关问题的更新为准。


本文保留当时的启动故障与恢复记录，操作前仍需核对现场脚本版本。

发生日期：2026-09-17

涉及端：DREAM 导航、G1 真机

状态：原因已确认，恢复路径已明确

<a id="e-b2-s1"></a>

### 1. 现象

DREAM 一键启动进入机器人站立人工闸门后，后续 `arm`、地图、孪生和审核页 `9882` 均未启动。

机器人仍可通过 `adapter` 窗口中的两次 Enter 完成站立，但导航编排已经退出，继续等待不会恢复后续流程。

关键报错：

```text
POSE ready file was not created; navigation remains locked.
```

<a id="e-b2-s2"></a>

### 2. 时间线

- 16:12:52：工作流出现人工 Enter 闸门；
- 16:22:52 左右：600 秒等待上限到期，编排退出；
- 16:25：现场才按下 Enter，已经晚于脚本超时；
- Enter 仍能作用于存活的 `adapter`，但无法让已经退出的编排继续创建后续窗口。

<a id="e-b2-s3"></a>

### 3. 排查证据

- 超时值来自 `tools/g1_fixed_map_relocalize_navigation_workflow.sh:563`；
- `adapter` 进程在编排退出后仍然存活，因此机器人还能站立；
- `arm`、地图、孪生和 `web`（9882）窗口没有创建，说明退出的是外层工作流，而不是单纯页面未打开；
- 报错明确指出 POSE ready 文件未在期限内生成。

<a id="e-b2-s4"></a>

### 4. 根因

人工操作超过脚本硬编码的 600 秒等待期限。

后续按 Enter 只能操作仍存活的 `adapter`，不能恢复已经退出的工作流。现场看到机器人站起来，容易误判为启动仍在继续。

<a id="e-b2-s5"></a>

### 5. 恢复方法

先停止残留工作流，再使用恢复入口：

```bash
cd <DREAM_ROOT>
bash tools/g1_three_party_oneclick.sh stop
bash tools/g1_three_party_oneclick.sh resume
```

`resume` 只重启 DREAM 编排，不重复启动仍在运行的 SONIC、导航 relay、相机和灵巧手。

不能直接执行 `resume`：旧工作流会话仍存在时，脚本会拒绝恢复。

<a id="e-b2-s6"></a>

### 6. 后续预防

- 人工闸门出现后立即记录时间，必须在 600 秒内完成；
- 第一次 Enter 用于接管，等 stage 1 稳定后再按第二次 Enter 进入 POSE；
- 超时后不要因为机器人仍能站立就继续等待，应先确认外层编排是否已经退出；
- 面板日志由导航机 tmux 托管并通过 `pipe-pane` 落盘，避免面板重启后看不到超时报错；
- 面板“站立 Enter”每次只发送一个 Enter，不会代替现场完成解肩带确认。
