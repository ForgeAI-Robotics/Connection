`$TIANJI_RUNTIME/config/tianji_cleanup.yaml` 是本阶段**待提供的私有启动配置**，不是已存在的可用文件；该运行工作区内的 `config/networks.yaml`、必要执行配置和私有凭据也要先按本实例建立。不能只带 `--config` 而仍把 `CONNECTION_WORKSPACE` 留在 G1 根目录，否则媒体、学习和日志仍可能落到 G1 默认路径。启动失败只能修专属配置／代码，不能借用 G1 tmux 会话、面板“一键启动”或重启主机；只按明确 PID／会话停止自己的进程。

远端同事访问本机监听端口时可建立独立隧道；前提是两端所选端口均未占用：

```bash
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:15000:127.0.0.1:15000 fq@192.168.31.144
```

## 3. 清理桌面 Skill 的目标流程

任务触发词固定为 `清理桌面（天机）`。建议独立包名 `tianji_cleanup`、SOP ID `tianji.cleanup_table`、首版版本 `1`；这些是待实现的登记要求，不是当前已经存在的目录项。

按下面的执行步骤生成任务状态。当前只通过 API 返回步骤列表，后续网页可复用同样的显示名：

```text
任务：清理桌面（天机）

○ 初始化任务
○ 读取天机现场与能力

点位 1
○ 导航到桌边点位 1
○ 获取头部新图，判断有无垃圾
○ 抓取垃圾
○ 核验垃圾已抓住、抓取动作已停止
○ 导航到垃圾桶前
○ 投放垃圾
○ 核验垃圾已投放、投放动作已停止
○ 返回点位 1
○ 重新取图，确认当前区域已清理干净

点位 2
○ 导航到桌边点位 2
○ 观察 → 有垃圾则抓取 → 运送到同一桶 → 投放 → 返回复查

点位 3
○ 导航到桌边点位 3
○ 观察 → 有垃圾则抓取 → 运送到同一桶 → 投放 → 返回复查

○ 导航到等待点
○ 桌面清理完成
```

点位 2、3 的观察、抓取、核验、导航、投放、核验、返回和复查与点位 1 一样，实际 API 中也必须逐项展开，不能把一组动作藏成一个只返回成功的脚本。

### 3.1 条件、循环和点位

- 沿桌边同一直线的三个桌面作业点依次处理，垃圾桶在点位 1 旁；桶前站位及等待点单独标定。沿用已确认的平行往返与朝向要求，实际路径／模式由天机 NAV 核实。
- 点位配置只维护一份，记录 `target_id`、`goal_xyt=[x,y,yaw]`、坐标系／地图身份、支持的运动模式。使用现场标定值，不填 G1 冰箱／中转点坐标，不把示意图像素当坐标。
- 有垃圾：选择本次受支持目标、单臂和详细 `prompt`，执行一次抓取，再去桶前投放。无垃圾：记录本点观察依据，进入下一点。图片无效、遮挡或判断不清：重观察或进入人工处理，不能当成无垃圾。
- 每次投放后返回原清理点，用新帧复查；仍有垃圾则创建下一轮独立步骤。点位 3 也要复查，不能因为执行了一次投放就宣称桌面已清空。
- 每轮观察／抓取／投放具有独立步骤、尝试和命令身份。循环次数、重复无进展和等待预算在天机 Skill 配置中明确并回写；达到预算暂停处理，不能静默完成或无限派发。
- 只有三个点位均有有效的无垃圾观察、没有未投放的持物、所有必要动作及停止核验通过、等待点到位核验通过，才能报告本轮清理完成。范围仅为三个已标定区域，不扩大为全部桌面或任意垃圾类别。

### 3.2 观察、效果与交接

头图从天机真实头部接口取新帧，保存来源、帧身份、时间及 VLM 原判断；到站后的图须晚于原 NAV 完成边界，复查不能重复使用旧帧。VLM 判断有无垃圾不替代抓取／投放效果证据。模型与提示词绑定天机任务配置，不切换 G1 的全局观察源。

抓取和投放遵守[天机操控合同](接口说明_天机操控.md)：抓取按已约定的 HIL-SERL 连续确认和停止事实核验，不额外要求撤手／携带姿态；目标匹配、抓后持有至导航到站按现有业务假设明示，不伪称实时识别。投放仍须确认释放、落桶、动作停止和合同规定的退出事实。

抓取 PASS 后，由天机流程适配完成真实执行端交接再派发 NAV；独立原子结果中的 `navigation_allowed=false` 表示它没有授权后续动作，不能在包装层简单改成 true。NAV 到站也不自动启动 VLA。天机底盘和机械臂原控制归属／准入仍有效，不调用 G1 的 SONIC 选源、O6 或网关来完成天机交接。

### 5.2 整轮任务 API 案例

下面复用**已经存在的 API 路径**，但天机任务登记、专属后端和配置尚需第 4 节实现。当前主 G1 实例不可使用这些例子测试天机，不得把地址改成 `:5000`、`:8888` 或从 G1 网页发布。首次只连无硬件输出的天机测试后端，确认完整计划及终态；切真实后端需现场安排并记录实际派发配置。

```bash
export TIANJI_BRAIN_URL=http://127.0.0.1:15000

# 先核对连接的是本次隔离实例及已登记的天机 SOP。
curl --fail-with-body "$TIANJI_BRAIN_URL/health"
curl --fail-with-body "$TIANJI_BRAIN_URL/api/sops"

# 新任务只发布一次。更换测试轮次时换新 task_id；断线时先查原任务。
curl --fail-with-body -H 'Content-Type: application/json' \
  -X POST "$TIANJI_BRAIN_URL/publish_task" \
  --data '{"task":"清理桌面（天机）","task_id":"tianji-cleanup-001","refresh":false}'

# GET 返回该隔离实例的当前任务；核对 task_id 后才解释其状态。
curl --fail-with-body "$TIANJI_BRAIN_URL/api/task_status"

# 以下是各自独立的操作示例，按现场需要选用，不按顺序批量执行。
curl --fail-with-body -H 'Content-Type: application/json' \
  -X POST "$TIANJI_BRAIN_URL/api/task_pause" \
  --data '{"task_id":"tianji-cleanup-001"}'

curl --fail-with-body -H 'Content-Type: application/json' \
  -X POST "$TIANJI_BRAIN_URL/api/task_continue" \
  --data '{"task_id":"tianji-cleanup-001"}'

curl --fail-with-body -H 'Content-Type: application/json' \
  -X POST "$TIANJI_BRAIN_URL/api/task_cancel" \
  --data '{"task_id":"tianji-cleanup-001"}'
```

HTTP 200、`accepted=true` 和健康状态都不代表动作或任务成功。发布后核对 `task_id`、所选天机 SOP／版本、执行后端、步骤及原命令；只有 Runtime 正式核验全部必要步骤通过才完成。接手者须记录实际返回字段和客户端判断规则，不能根据模糊文本“成功”判定。

### 5.3 任务控制与恢复的硬边界

- 暂停、继续、取消绑定原任务；取消某轮天机任务只能操作该轮已提交的天机命令，不能向 G1 或新一轮任务广播停止。
- 发布或原子 POST 超时后保留原 ID，先查询原任务／命令。网络异常、404、服务重启或忙碌不能单独证明动作没执行，不自动重发或换 ID 再试。
- 抓取成功、策略停止、导航接管和整轮任务完成分别记录。取消已受理不等于机器人已停；停止／释放未知时保留未知与失败，不删除账本。
- 查询原命令不触发下一次动作。只有原 Runtime 经核验决定推进；暂停、取消或换命令后的迟到成功／观察／取消回执不能推动当前步骤或停止新命令。
- 恢复保留原任务快照及尝试。确认需要新尝试后使用新 `command_id`，保留旧失败，不通过手工写成功、跳过未知或关掉核验凑通流程。
