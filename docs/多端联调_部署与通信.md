18:45 的真机 NX 与服务器双向对照包含 400 次正式 HTTP 和 200 次 ICMP，零超时／丢包；每方向每指标 50 对配对样本。服务器使用有线接口时，网络往返中位数约减少 2–3ms，轻量 HTTP 约减少 5–6ms；完整状态查询收益较小。**NX 本身仍通过无线连接**，不能称全链路有线或全部业务提速同一比例。[D4](#e-d4)

状态查询还包含服务处理及操控端对导航的内部调用，不能用健康请求代表交接或控制时延，也不能简单相减两个独立中位数求转发开销。云端大图片上传与模型等待另见[模型本地／云端对照](多端联调_模型接入与评测.md#本地与云端)，不在本文复制模型性能表。

## 协议与接口通信基准：采样方法和分阶段归因

证据日期：2026-10-10。本节保留对应条件下的完整排查与复验内容；后续变化以文首验证概览及相关问题的更新为准。


发生日期：2026-10-10，约 11:10–11:21，北京时间。

范围：当前配置服务的只读健康探测、当前接待仿真服务的局域网 HTTP 采样、隔离进程之间的真实 TCP 协议基准。不提交实体动作，不部署远端程序，不重启现有服务。这里的协议基准不等于真机三端验收。

<a id="e-d1-s1"></a>

### 1. 结论与选择

**2026-10-10 补充决策边界：保留当前 HTTP，不据本轮微基准批准协议迁移。先补齐真实业务的分段计时，再判断是否需要优化连接、通知或协议。** 本轮没有测得真机 VLA 推理时间，也没有真机三端 HTTP/gRPC 对照，不能认定 HTTP 是瓶颈或 gRPC 必须迁移。

上午提出的低改动候选是：HTTP 保留命令提交与原命令查询，增加 SSE 状态通知，网页也使用 SSE；断线时补查原命令。该候选仅在真实链路确认结果发现等待影响目标后实施，**不是已验证的生产选型**。本轮没有修改生产通信实现。历史真机日志复核与下一轮归因方法见第 8 节。

- 本机小报文单次调用中 gRPC + Protobuf 更快，但相对现有 urllib 的中位数收益约 0.20 ms；不是当前数百毫秒结果发现等待的主要解决手段。
- SSE、预连接 WebSocket、gRPC 流均消除了周期轮询等待。本次 Python 实现下，推送之间的差异远小于轮询与推送之间的差异。
- HTTP 提交 + gRPC 通知没有显示出相对 HTTP + SSE 的明确性能收益，却需要增加 Protobuf、代码生成和第二套服务入口。当前不优先采用这种混合方式。
- WebSocket 适合未来持续双向交互。当前大脑提交低频命令、下游返回状态的模式，使用 HTTP + SSE 更容易保留已有接口。
- 当前实际可达的 SIMPLE 接待服务返回 HTTP/1.0，并关闭响应连接。**只将客户端换成 Session 不能获得连接复用**，需要服务端与客户端一起实现、验证。
- 如果以后接口规模、跨语言开发或持续数据流需求增加，再评估大脑与 NAV/VLA 使用 gRPC、网页继续 HTTP/SSE。不能凭本次小样本承诺真机长尾或硬实时性能。

任务控制、原命令身份、核验与恢复规则仍以[大脑接口](接口说明_大脑%20Brain.md)为准。SSE、WebSocket、gRPC 只改变传输与通知方式，不建立新的业务状态权威。

### 3. 隔离基准方法

脚本：[benchmark_communication.py](../scripts/benchmark_communication.py)。

- 独立 Python 客户端进程和服务端进程，以回环 TCP 通信；没有使用 mock HTTP 调用。
- 同一服务端进程提供 aiohttp HTTP/SSE/WebSocket 和 grpc.aio 服务，使用同一内存命令存储、完成时刻及消息字段。该存储只是实验装置，没有生产级账本、控制器或持久化能力。
- 单次调用对照：项目现有 HttpClient/urllib、requests.Session、HTTPX Client、gRPC 包装 JSON、gRPC 类型化 Protobuf。JSON 和 Protobuf 表达相同字段；服务端均解码、重新编码，客户端均校验返回内容。
- 单次调用为串行小负载；每组预热 5 次，3 轮调整执行顺序。直接回环的每种报文/方案共 480 样本，增加 10 ms 延迟的每种方案 180 样本，增加 50 ms 的每种方案 72 样本。
- JSON 报文约 539 B、4.4 KB、65.8 KB；较大报文是诊断文本，不是图像、点云或完整业务结果。小报文类型化 Protobuf 为 344 B。
- 所有协议均无 TLS、无压缩；gRPC channel 提前连接并预热。没有测试 HTTP/2 + JSON 的独立 HTTP 客户端，也没有测试 DDS、MQTT、HTTP/3。
- 延迟场景用用户态 TCP 转发器，每方向延后 5 ms 或 25 ms。**它不是网络层 netem，不延迟原始 TCP 握手，也不模拟丢包、重传、带宽或 Wi-Fi 竞争。** 结果只能说明人为增加消息传播等待后的趋势。
- 通知测试 8 个并发模拟命令，每方案、每延迟场景 64 个样本，且使用相同随机种子。通知时间取“服务端写入完成状态 → 客户端解析得到终态”，两个进程使用同机单调时钟，避免跨机时钟误差。
- 第一批命令耗时 50–450 ms。随后增加 50–1,050 ms 分布，覆盖完整一秒轮询周期，避免把短任务样本的平均轮询等待当成通用结论。下面通知主表使用后者。
- SSE 为 HTTP 提交后订阅；gRPC 流为 gRPC 提交后订阅；混合方案为 HTTP 提交后订阅 gRPC 流。均能在订阅晚于完成时返回当前终态。
- WebSocket 同时测“提交后建连接”和“提交前已建连接”；预连接案例用于比较连接已就绪时的通知延迟，建连接时间不计入该案例任务时间。

环境：Python 3.10.18，Linux x86_64；grpcio/grpcio-tools 1.76.0、protobuf 6.33.6、aiohttp 3.14.4、httpx 0.28.1、requests 2.34.2。使用独立临时环境，未修改项目依赖。

| --- | ---: | ---: | ---: |
| 当前 urllib + JSON | 0.451 / 0.474 | 0.472 / 0.545 | 0.872 / 1.027 |
| requests.Session + JSON | 0.571 / 1.098 | 0.544 / 1.286 | 1.005 / 1.128 |

### 6. 落地条件与未验证范围

建议先在现有执行适配器边界实施状态订阅，保留 HTTP 提交和原命令查询。网页订阅大脑事件，NAV/VLA 不相互触发动作，Runtime 仍是任务状态唯一权威。

实施前需要两端明确事件身份与顺序、重连后补查、终态保留、陈旧结果拒绝、消费积压和连接关闭规则。断流、gRPC deadline 或调用取消均不能冒充机器人停止，具体业务语义引用[大脑任务控制与恢复](接口说明_大脑%20Brain.md)。本实验装置未实现生产级重连、持久化与控制交接，不以其零错误结果证明这些能力。

如果近期不能增加推送，可把 100–200 ms 活动命令轮询作为待测过渡方案，但要先接通实际配置传递、确认服务负载；当前代码的接待请求没有传递 YAML 中的两个轮询间隔字段，实际使用适配器默认的 0.5/1.0 秒。

连接复用要同时核实服务端版本、响应长度与连接生命周期，不能只添加一个请求头或切换客户端。当前真机两端不可达，因此它们的响应版本、连接复用和请求长尾均未在本轮测得。

#### 下一轮应先测什么

先定义需要改善的指标：任务发布到接受、接受到开始动作、动作完成到大脑获知、动作完成到网页显示，以及完整任务时长分别统计；不能用导航行走时间较长来掩盖启动或停止的长尾。

| 分段 | 需要的观测 |
| --- | --- |
| 大脑任务理解／规划 | 实际模型调用起止、排队、调用次数；固定 SOP 不虚构模型耗时，异步反思不自动计入执行关键路径 |
| HTTP 提交／查询 | 客户端单次请求起止、连接是否复用、报文大小、状态码；远端入口／出口的对应处理时长 |
| 导航准备与运动 | 接受、审批结束、规划完成、控制器采纳、开始运动、停止、终态；不能把它们合成通信时间 |
| 操控观测与推理 | 图像采集、编码、传输、推理队列、预处理、模型计算、后处理、动作片段到达本地执行器 |
| 完成通知与交接 | 终态生成、轮询发现、大脑核验、控制交接、网页收到状态；对齐原 command_id |

沿现有日志和命令身份补时间字段即可，不要求先部署新的监控平台。各进程内部用单调时钟统计时长；跨机器时间差必须处理时钟偏差与不确定度。客户端往返耗时减服务端处理耗时仍可能包含客户端及代理排队，不标为纯网络耗时。CUDA 异步执行的模型计算计时需要正确的 GPU 计时边界，不能只统计算子提交时间。

建议验证顺序（尚未执行）：

1. 固定软件、模型、任务、场地与负载，保持 HTTP 原样建立基线；记录冷启动与预热结果。
2. 先做无实体动作的观测回放／离线推理和隔离服务测试，比较原 HTTP、支持复用的 HTTP、必要时的 gRPC，使用相同业务处理和真实报文。健康接口不能代替业务接口。
3. 在已安排并具备现场条件的真机联调中采集完整时间线。首批 10–20 次同类动作仅用于发现问题；报告全部失败、重试和超时，小样本不宣称 p99 稳定。后续按波动、风险和目标决定样本量，不为统计数量重复无必要实体动作。
4. 确认瓶颈后一次只改一个变量，并复测相同指标。多机器人压力与网络故障先在隔离模拟执行器验证，不向真机并发重复发送动作。

选型门槛：HTTP 若满足延迟与容量目标则保留；若通知等待主导，先验证 HTTP 上的推送或受控轮询；若模型或导航执行主导，优化对应环节；只有通信栈在目标负载下占据显著预算，且等条件对照证明替换有收益、恢复语义无回归，才进入局部协议迁移。跨语言和接口治理可以另作架构理由，但不能冒充本次已经证明的性能收益。

本次只增加离线审计脚本和分析记录，未修改生产通信、重启服务或执行真机动作。

#### 路由核对与结论

- 大脑访问两个地址，路由均为 `local ... dev lo`，本机健康都约 0.6 ms；改目标 IP 没有消除新的网络跳数。

- NX 和旧机的邻居表均确认：目标无线地址对应目标无线网卡 MAC，目标有线地址对应目标 `eno1` MAC；本次不是两个地址落到同一网卡的假对照。

本轮只测目标地址差异，不改大脑访问 NX 的目标；也未把来源端无线改为有线。
