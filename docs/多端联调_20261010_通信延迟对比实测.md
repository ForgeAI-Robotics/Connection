# 多端联调：通信延迟对比实测

发生日期：2026-10-10，约 11:10–11:21，北京时间。

范围：当前配置服务的只读健康探测、当前接待仿真服务的局域网 HTTP 采样、隔离进程之间的真实 TCP 协议基准。不提交实体动作，不部署远端程序，不重启现有服务。这里的协议基准不等于真机三端验收。

## 1. 结论与选择

**2026-10-10 补充决策边界：保留当前 HTTP，不据本轮微基准批准协议迁移。先补齐真实业务的分段计时，再判断是否需要优化连接、通知或协议。** 本轮没有测得真机 VLA 推理时间，也没有真机三端 HTTP/gRPC 对照，不能认定 HTTP 是瓶颈或 gRPC 必须迁移。

上午提出的低改动候选是：HTTP 保留命令提交与原命令查询，增加 SSE 状态通知，网页也使用 SSE；断线时补查原命令。该候选仅在真实链路确认结果发现等待影响目标后实施，**不是已验证的生产选型**。本轮没有修改生产通信实现。历史真机日志复核与下一轮归因方法见第 8 节。

- 本机小报文单次调用中 gRPC + Protobuf 更快，但相对现有 urllib 的中位数收益约 0.20 ms；不是当前数百毫秒结果发现等待的主要解决手段。
- SSE、预连接 WebSocket、gRPC 流均消除了周期轮询等待。本次 Python 实现下，推送之间的差异远小于轮询与推送之间的差异。
- HTTP 提交 + gRPC 通知没有显示出相对 HTTP + SSE 的明确性能收益，却需要增加 Protobuf、代码生成和第二套服务入口。当前不优先采用这种混合方式。
- WebSocket 适合未来持续双向交互。当前大脑提交低频命令、下游返回状态的模式，使用 HTTP + SSE 更容易保留已有接口。
- 当前实际可达的 SIMPLE 接待服务返回 HTTP/1.0，并关闭响应连接。**只将客户端换成 Session 不能获得连接复用**，需要服务端与客户端一起实现、验证。
- 如果以后接口规模、跨语言开发或持续数据流需求增加，再评估大脑与 NAV/VLA 使用 gRPC、网页继续 HTTP/SSE。不能凭本次小样本承诺真机长尾或硬实时性能。

任务控制、原命令身份、核验与恢复规则仍以[大脑接口](接口说明_大脑%20Brain.md)为准。SSE、WebSocket、gRPC 只改变传输与通知方式，不建立新的业务状态权威。

## 3. 隔离基准方法

脚本：[benchmark_communication.py](../scripts/benchmark_communication.py)。

- 独立 Python 客户端进程和服务端进程，以回环 TCP 通信；没有使用 mock HTTP 调用。
- 同一服务端进程提供 aiohttp HTTP/SSE/WebSocket 和 grpc.aio 服务，使用同一内存命令存储、完成时刻及消息字段。该存储只是实验装置，没有生产级账本、控制器或持久化能力。
- 单次调用对照：项目现有 HttpClient/urllib、requests.Session、HTTPX Client、gRPC 包装 JSON、gRPC 类型化 Protobuf。JSON 和 Protobuf 表达相同字段；服务端均解码、重新编码，客户端均校验返回内容。
- 单次调用为串行小负载；每组预热 5 次，3 轮调整执行顺序。直接回环的每种报文/方案共 480 样本，增加 10 ms 延迟的每种方案 180 样本，增加 50 ms 的每种方案 72 样本。
- JSON 报文约 539 B、4.4 KB、65.8 KB；较大报文是诊断文本，不是图像、点云或完整业务结果。小报文类型化 Protobuf 为 344 B。
- 所有协议均无 TLS、无压缩；gRPC channel 提前连接并预热。没有测试 HTTP/2 + JSON 的独立 HTTP 客户端，也没有测试 DDS、MQTT、HTTP/3。
- 延迟场景用用户态 TCP 转发器，每方向延后 5 ms 或 25 ms。**它不是网络层 netem，不延迟原始 TCP 握手，也不模拟丢包、重传、带宽或 Wi-Fi 竞争。** 结果只能说明人为增加消息传播等待后的趋势。
- 通知测试 8 个并发模拟命令，每方案、每延迟场景 64 个样本，且使用相同随机种子。通知时间取“服务端写入完成状态 → 客户端解析得到终态”，两个进程使用同机单调时钟，避免跨机时钟误差。
- 第一批命令耗时 50–450 ms。随后增加 50–1,050 ms 分布，覆盖完整一秒轮询周期，避免把短任务样本的平均轮询等待当成通用结论。下面通知主表使用后者。
- SSE 为 HTTP 提交后订阅；gRPC 流为 gRPC 提交后订阅；混合方案为 HTTP 提交后订阅 gRPC 流。均能在订阅晚于完成时返回当前终态。
- WebSocket 同时测“提交后建连接”和“提交前已建连接”；预连接案例用于比较连接已就绪时的通知延迟，建连接时间不计入该案例任务时间。

环境：Python 3.10.18，Linux x86_64；grpcio/grpcio-tools 1.76.0、protobuf 6.33.6、aiohttp 3.14.4、httpx 0.28.1、requests 2.34.2。使用独立临时环境，未修改项目依赖。

## 4. 单次请求结果

下表为直接回环，单位 ms，每格为 p50 / p95，3 轮合并。分位数采用脚本的排序取值方法，不能从这些样本推断生产 SLA。

| 客户端与报文方式 | 约 539 B JSON 对应报文 | 约 4.4 KB JSON 对应报文 | 约 65.8 KB JSON 对应报文 |
| --- | ---: | ---: | ---: |
| 当前 urllib + JSON | 0.451 / 0.474 | 0.472 / 0.545 | 0.872 / 1.027 |
| requests.Session + JSON | 0.571 / 1.098 | 0.544 / 1.286 | 1.005 / 1.128 |
| HTTPX Client + JSON | 0.486 / 1.135 | 0.505 / 1.161 | 0.994 / 1.169 |
| gRPC + JSON 包装 | 0.290 / 0.619 | 0.589 / 0.698 | 1.227 / 1.569 |
| gRPC + Protobuf | 0.251 / 0.270 | 0.280 / 0.324 | 0.426 / 0.456 |

服务端连接计数确认：直接回环每组 160 次正式请求中，urllib 使用 160 条连接，两个连接池客户端各使用 1 条连接。但在本机低延迟、小负载下，连接池客户端的库开销抵消了建连节省，不能写成“连接池实测一定更快”。

小报文增加消息往返等待后，各方案中位数如下：

| 客户端 | 增加 10 ms（ms） | 增加 50 ms（ms） |
| --- | ---: | ---: |
| 当前 urllib | 12.162 | 52.434 |
| requests.Session | 12.008 | 52.183 |
| HTTPX Client | 11.645 | 52.088 |
| gRPC + JSON 包装 | 11.336 | 51.760 |
| gRPC + Protobuf | 11.257 | 51.720 |

因此，本实验支持“gRPC + Protobuf 在本次单次请求基准中更快”，不支持“换协议能消除网络传播、导航执行或轮询等待”。也不能把当前短连接与 gRPC 的差异全部归因于 HTTP 协议。

## 5. 完成通知结果

模拟动作耗时 50–1,050 ms，8 并发，每行每场景 64 样本。单位 ms，每格为“完成到收到终态”的 p50 / p95。轮询方案均使用连接池，因此这里主要对照通知机制。

| 通知方式 | 直接回环 | 增加 10 ms 往返等待 | 增加 50 ms 往返等待 |
| --- | ---: | ---: | ---: |
| HTTP 每 500 ms 查询 | 249.307 / 438.491 | 269.539 / 452.611 | 370.151 / 568.362 |
| HTTP 每 1,000 ms 查询 | 530.326 / 904.515 | 558.761 / 932.933 | 601.081 / 1024.995 |
| HTTP 每 100 ms 查询 | 47.274 / 95.905 | 62.081 / 116.981 | 91.136 / 173.489 |
| HTTP 提交 + SSE | 0.341 / 0.478 | 5.726 / 6.425 | 26.185 / 26.896 |
| HTTP 提交 + 新建 WebSocket | 0.255 / 0.384 | 5.577 / 6.104 | 26.093 / 27.343 |
| HTTP 提交 + 预连接 WebSocket | 0.257 / 0.312 | 5.656 / 6.207 | 25.960 / 26.480 |
| gRPC 提交 + gRPC 流 | 0.685 / 0.919 | 6.315 / 6.864 | 26.526 / 27.161 |
| HTTP 提交 + gRPC 流 | 0.695 / 1.034 | 6.291 / 6.758 | 26.507 / 27.433 |

直接回环的 64 个模拟命令，500 ms 轮询共读取状态 162 次，100 ms 轮询读取 431 次。推送组没有重复状态 GET，但仍有提交、订阅和连接成本；“零查询”不等于零网络请求。

第一批较短任务中，在增加 50 ms 等待时，新建 WebSocket 的 p95 为 54.54 ms，预连接为 26.67 ms；补测更长任务后差距缩小。说明是否预连接、任务多快完成也会影响观察结果，不能泛化成某协议总是更慢。

通知基准都是 aiohttp/grpc.aio 异步 Python 实现。本次 SSE 与 WebSocket 的亚毫秒优势不足以证明它们在所有语言和部署中优于 gRPC；本次足以证明的是，当前量级下消除周期轮询比更换单次请求编码更有价值。

## 6. 落地条件与未验证范围

建议先在现有执行适配器边界实施状态订阅，保留 HTTP 提交和原命令查询。网页订阅大脑事件，NAV/VLA 不相互触发动作，Runtime 仍是任务状态唯一权威。

实施前需要两端明确事件身份与顺序、重连后补查、终态保留、陈旧结果拒绝、消费积压和连接关闭规则。断流、gRPC deadline 或调用取消均不能冒充机器人停止，具体业务语义引用[大脑任务控制与恢复](接口说明_大脑%20Brain.md)。本实验装置未实现生产级重连、持久化与控制交接，不以其零错误结果证明这些能力。

如果近期不能增加推送，可把 100–200 ms 活动命令轮询作为待测过渡方案，但要先接通实际配置传递、确认服务负载；当前代码的接待请求没有传递 YAML 中的两个轮询间隔字段，实际使用适配器默认的 0.5/1.0 秒。

连接复用要同时核实服务端版本、响应长度与连接生命周期，不能只添加一个请求头或切换客户端。当前真机两端不可达，因此它们的响应版本、连接复用和请求长尾均未在本轮测得。

### 未出现 accepted 事件的五次提交

继续核对同一 command_id 的 `CALL/end`，五次均有 `/v1/navigation/goals` 提交请求的错误响应。之前只写“未匹配接受回执”，不能理解成丢回包或没有 HTTP 响应。

| 命令 | 提交结果 | 开始到错误日志 | 源日志行 |
| --- | --- | --- | --- |
| `nav-relay2-26579ba84eec` | HTTP 409，`INVALID_LEG_ORDER` | 50 ms | 676、677 |
| `nav-relay2-26579ba84eec-r1` | HTTP 409，`INVALID_LEG_ORDER` | 48 ms | 685、686 |
| `nav-relay2-26579ba84eec-r2` | HTTP 409，`INVALID_LEG_ORDER` | 130 ms | 694、695 |
| `nav-relay2-26579ba84eec-r3` | HTTP 409，`INVALID_LEG_ORDER` | 93 ms | 703、704 |
| `nav-table2-c6125691e7cf-r1` | HTTP 500，`name 'expected_goal' is not defined` | 78 ms | 741、742 |

这些时长使用同一大脑日志的起止时间戳计算，包含错误处理和日志开销，不与 `duration_s` 的单调时钟边界混用。四次 409 是导航要求同任务 table2 成功后才允许 relay2，而当时前段被人工跳过；大脑记录 `submission_rejected`。一次 500 是导航服务异常响应，不能据此判断动作未执行；大脑在第 743 行记录 `unconfirmed`，命令为 UNKNOWN。

这五次不能作为“提交丢响应”或“轮询无响应”的故障样本。历史记录另有服务重启后连接被拒、原命令不可查和取消未确认，属于后续查询／恢复问题，应独立归类；目前没有完整逐请求计时，不能给出全部轮询的响应率或延迟分布。

连接阶段另查到原始观测：`logs/2026-10-09/joint_round3.jsonl` 第 16 行，14:50:52，`source=nav`，错误为 `[Errno 111] Connection refused`。这是联调观察器连接导航端被拒的记录，不是大脑 POST 丢响应的直接记录；可以确认当次 TCP 连接未建立，不能仅凭客户端错误确认是进程停止、监听地址错误还是网络设备主动拒绝。`commands={}` 是错误记录中的空字段，不能当作导航端返回“没有命令”。`joint_round2.jsonl` 第 82 行则是观察器连接 Brain 被拒，不能算作导航错误。

统计需同时标记操作类型（提交／查询／停止／健康检查）和故障阶段（连接拒绝／连接超时／连接后读写异常／HTTP 错误响应／业务拒绝／执行失败）。端口能连接、健康接口返回、业务请求被接收、动作完成是不同证据。当前没有足够证据把这些连接拒绝记录归为“业务服务健康在线、已收到请求却不回包”。

最慢配对为 `nav-relay3-d91990613a87-r1`，源日志第 536、537 行；收到的状态是 `waiting_operator_approval`。仅凭该状态不能把 1,221 ms 归因为人工等待或网络异常，需补远端请求处理计时。

现有 `OutboundCall.duration_s` 从创建调用记到命令结束，包含下游执行和状态等待，不能当成 HTTP 请求耗时。核对实现：`src/shared/brain_journal.py` 的 `OutboundCall`，以及 `src/brain/adapters/dream_client.py`、`vla_client.py` 的提交与轮询路径。没有足够分段证据比较真机 VLA 推理与传输占比。

### 下一轮应先测什么

先定义需要改善的指标：任务发布到接受、接受到开始动作、动作完成到大脑获知、动作完成到网页显示，以及完整任务时长分别统计；不能用导航行走时间较长来掩盖启动或停止的长尾。

| 分段 | 需要的观测 |
| --- | --- |
| 大脑任务理解／规划 | 实际模型调用起止、排队、调用次数；固定 SOP 不虚构模型耗时，异步反思不自动计入执行关键路径 |
| HTTP 提交／查询 | 客户端单次请求起止、连接是否复用、报文大小、状态码；远端入口／出口的对应处理时长 |
| 导航准备与运动 | 接受、审批结束、规划完成、控制器采纳、开始运动、停止、终态；不能把它们合成通信时间 |
| 操控观测与推理 | 图像采集、编码、传输、推理队列、预处理、模型计算、后处理、动作片段到达本地执行器 |
| 完成通知与交接 | 终态生成、轮询发现、大脑核验、控制交接、网页收到状态；对齐原 command_id |

沿现有日志和命令身份补时间字段即可，不要求先部署新的监控平台。各进程内部用单调时钟统计时长；跨机器时间差必须处理时钟偏差与不确定度。客户端往返耗时减服务端处理耗时仍可能包含客户端及代理排队，不标为纯网络耗时。CUDA 异步执行的模型计算计时需要正确的 GPU 计时边界，不能只统计算子提交时间。

建议验证顺序（尚未执行）：

1. 固定软件、模型、任务、场地与负载，保持 HTTP 原样建立基线；记录冷启动与预热结果。
2. 先做无实体动作的观测回放／离线推理和隔离服务测试，比较原 HTTP、支持复用的 HTTP、必要时的 gRPC，使用相同业务处理和真实报文。健康接口不能代替业务接口。
3. 在已安排并具备现场条件的真机联调中采集完整时间线。首批 10–20 次同类动作仅用于发现问题；报告全部失败、重试和超时，小样本不宣称 p99 稳定。后续按波动、风险和目标决定样本量，不为统计数量重复无必要实体动作。
4. 确认瓶颈后一次只改一个变量，并复测相同指标。多机器人压力与网络故障先在隔离模拟执行器验证，不向真机并发重复发送动作。

选型门槛：HTTP 若满足延迟与容量目标则保留；若通知等待主导，先验证 HTTP 上的推送或受控轮询；若模型或导航执行主导，优化对应环节；只有通信栈在目标负载下占据显著预算，且等条件对照证明替换有收益、恢复语义无回归，才进入局部协议迁移。跨语言和接口治理可以另作架构理由，但不能冒充本次已经证明的性能收益。

### 9.4 确实存在的连接／服务可用性问题

10 月 8～9 日 `dream/monitor.log` 内有 10 条 `Connection refused`、3 条 `No route to host`、4 条未区分阶段的 `timed out`，以及 7 条记录下来的 HTTP 200。这里统计的是健康探测日志行，不是独立故障次数或全部请求数。

**不能计算为 17/24 的通信失败率。** 当前 `src/ops/services.py::_record_probe` 对正常探测保持静默，并抑制相同故障；旧版本记录策略也可能不同。还混有服务未启动、停机、重启和换网时段，无法据此计算在线期间可用性或停机比例。

### 9.5 当前决策

保留 HTTP。优先处理具体的导航执行失败、服务异常和上线就绪／地址配置问题；数据时效异常继续追到实际链路。给提交、查询、停止、健康检查分别补总请求数、连接失败、读写超时、HTTP 状态码、延迟和服务在线窗口，再评估在线期间通信故障率。追踪操作类型、命令身份和各端处理时间，无需先换协议。

本次只增加离线审计脚本和分析记录，未修改生产通信、重启服务或执行真机动作。
