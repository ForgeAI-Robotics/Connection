# 多端联调：两款官方小型 VLM 对照

发生日期：2026-10-20。用户要求下载并实测 Qwen3-VL-4B-Instruct-FP8 与 Qwen3.5-2B，评估约 10GB 显存、三路识图及 Connection 图片接口替代能力。两个候选分别放在 `<WORKSPACE>/Qwen3-VL-4B-Instruct-FP8` 与 `<WORKSPACE>/Qwen3.5-2B`，原 9B 模型和默认图片路由保留。

结论：两款模型的使用后显存分别约 **9.88／9.05 GiB**，预热后三路短字段各 **60/60 ≤5 秒**；但本轮标注题分别 **39/57、36/57**，同轮 9B 均 **54/57**。4B 的 16K 档不能接收原始双图请求；2B 在两个“目标不存在”的核验负例中高置信度误报存在。因此未将任何候选切成默认模型，也不将看图链路成功写成业务效果等价。

HF 直连及代理路径出现 TLS／连接错误，最终从 ModelScope 与 HF 镜像分段下载，复用已下载数据补齐重试耗尽的分段。镜像元数据中的 revision 与此前从官方确认的版本一致；全部权重及运行文件按该版本的 LFS SHA256／Git blob hash 校验通过。未复制仓库管理用 `.gitattributes`，未缺省任何模型权重。原始下载失败日志、元数据、完整校验清单均保留。

使用现有 vLLM 0.18.0 环境，两个候选使用各自发布的 tokenizer／图像处理器，没有借用 9B 的配置替换。无 CPU 权重卸载、无视觉裁剪。两端均 eager，`max_num_batched_tokens=8192`；`gpu_memory_utilization=0.20` 仅为启动显存准入参数，并非 10GB 硬限额。

4B 采用 16K 档是本轮的低显存取舍，不是其模型原生上下文能力上限。2B 与作为对照的 9B 均采用 64K、MTP-1。模型规模、结构、MTP 及上下文配置不同，本轮不是只改变数值精度的实验。

## 2. 实际测试范围和公平性

共 **688 次视觉 API 请求**：

- 两轮主对照各 316 次，共 632 次：每轮候选与 9B 各 158 次。
- Connection 原图接口两轮各 16 次；4B 双图超限后追加双方各 8 次的 4MP 复测，共 48 次。
- 隔离大脑 HTTP＋实时 MuJoCo 取图任务两轮各 4 次，共 8 次。

其中 1 次 4B 原始双图请求因输入超限被拒；其余 687 次返回生成结果，其中 1 次 2B 无格式约束回答达到 1024 tokens 上限被截断。即正常 `stop` 完成为 686 次，不能写成 688 次全部成功。健康检查、下载探测和文本模型调用不计入。

主对照沿用 19 道标注题，各重复 3 次；另有不强制格式的 19 次、原图开放描述 3 次、4MP 单路清单 5 次、三路清单 9 次、三路短字段 60 次以及 5 次预热。包含仿真图片、OCR 和一张用户桌面实拍图，有重复场景；不是 19 个独立机场现场样本。

同轮两端的图片字节、问题、采样和输出预算相同：temperature 0、top_p 0.95、presence_penalty 0、seed 42、max_tokens 1024，关闭 thinking。每次使用新图片 UUID 和前缀 salt；约束 JSON 只限定结构和类型，不提供正确答案。原图开放描述及原始接口测试未缩图；标注题、并发及明确标记的接口复测限制 4,194,304 像素。

测试在约 48GiB 的 RTX 4090 上，候选依次运行，与始终驻留的 9B 交替调用。服务器原有其他 GPU 作业，本次未停止它们，背景负载在两轮间发生变化；完整进程显存与 GPU 利用率采样保留。应比较每个候选与其同轮 9B，不把两轮时延当作完全隔离条件下的硬件排名，也不直接套用此前 FP8 的最快结果。

## 3. 显存与时延

每约 0.5 秒按 systemd 控制组所属 PID 采样 NVML，计算／图形进程按 PID 去重。启动、模型测试、接口测试、仿真及使用后空闲均覆盖；采样可能漏掉极短瞬时峰值。

| 显存项目 | 4B FP8 | 2B BF16 |
| --- | --- | --- |
| 加载完成、正式图片调用前 | 8.33 GiB | 7.58 GiB |
| 全部测试期间采样峰值 | **9.88 GiB** | **9.05 GiB** |
| 使用后短时空闲常驻 | **9.88 GiB** | **9.05 GiB** |
| 同轮 9B BF16 采样峰值 | 23.01 GiB | 23.01 GiB |

不是小时／天级常驻压力测试，也未在实体 24GB 卡上验证；本轮未联合运行 GR00T VLA，不能据这些数值承诺同卡控制时延。

| 预热后任务 | 4B 轮：9B → 4B | 2B 轮：9B → 2B |
| --- | --- | --- |
| 原图“桌面上有什么”，3 次中位数 | 9.86 → 8.61 秒 | 9.28 → 5.29 秒 |
| 4MP 单路完整清单，5 次中位数 | 4.66 → 2.94 秒 | 4.28 → 2.13 秒 |
| 三路完整清单，9 次 P95 | 10.30 → 6.31 秒 | 7.26 → 3.76 秒 |
| 三路短字段，60 次 P95 | 5.47 → **3.83 秒** | 3.86 → **2.20 秒** |
| 三路短字段 ≤5 秒 | 38/60 → **60/60** | 60/60 → **60/60** |
| 三路短字段预定义内容正确 | 60/60 → 60/60 | 60/60 → 60/60 |

短字段题仅问用户桌面图能否看见绿植、保温杯、手机支架，以及是否能确认拭子交接；交接应答 unknown。不是三个真实机器人，也不是机场交接现场识别验收。开放描述／完整清单未完成逐物人工标注，回答长度与遗漏也会影响耗时，不能把全部时差解释为计算加速。

冷启动单列：2B 首个实际图片请求 **40.55 秒**，第一次三路短字段约 **11.47～11.50 秒**；后续预热结果不能掩盖首次延迟。服务 HTTP 就绪不代表已完成实际图片和并发预热，本轮没有为生产增加自动预热／就绪门。

## 4. 识别质量与已确认退化

| 检查 | 同轮 9B（两轮均如此） | 4B FP8 | 2B BF16 |
| --- | --- | --- | --- |
| 约束输出标注题 | 54/57 | **39/57** | **36/57** |
| 不强制格式的标注题内容 | 18/19 | 13/19 | 12/19 |
| 不强制格式的严格裸 JSON | 14/19 | 19/19 | 14/19 |

57 是 19 道题的三次重复，不是独立样本量；不将这些比例表述为通用识别准确率。

- 4B：空桌误报 1 个物体且存在蓝色物体；正视角 5 个物体答 4 个，侧视角答 6 个。相对 9B 新增失败题为 `empty`、`head`、两个 `repeat_head` 与 `side`。
- 2B：正视角 5 个答 4 个，空桌答 1 个，两图移除数量从应为 1 答成 2，双视角同场景计数答 4。相对 9B 新增失败题为 `difference`、`empty`、`head`、两个 `repeat_head` 与 `two_views_head`。
- 双视角空桌误计 1 个是原 9B 也存在的错误，两款小模型均未修复。
- 2B 在无格式约束的 `two_views_empty` 输出数组而非要求的对象；`two_views_head` 反复生成物体编号直至 1024 tokens 截断。强制 schema 可以约束结构，但其对应计数仍然错误，不能用格式通过替代内容通过。

用户桌面图的三个定向标注问题（物品存在、白色充电器数量、不可见信息应 unknown）两款均通过。但 4B 的原图开放描述出现“支架上似乎有手机”等不可靠补充；开放描述未完整人工评分，不能把定向题通过外推为所有细节正确。

## 5. Connection 接口与仿真

接口测试覆盖现场描述、Slaver 描述、双图桌面关系、抓放图片核验、候选物体识别。测试进程去掉云端密钥并阻止非本机图像模型请求，仅修改隔离端点；文字模型与生产配置不变。

| 检查 | 4B FP8 | 2B BF16 |
| --- | --- | --- |
| 原始图片接口正常返回 | 7/8 | 8/8 |
| 失败原因 | 双图输入 25,462 tokens 超出 16,384 | 无传输失败 |
| 单独 4MP 接口复测 | 8/8 正常返回 | 未因输入上限触发该复测 |
| 三类核验负例预定义字段 | 3/3 通过 | **1/3 通过** |
| 实时 MuJoCo 看图任务 | 2/2 succeeded | 2/2 succeeded |
| 实验工作区配置按字节恢复 | 是 | 是 |

原始双图拒绝日志：`ValueError: Input length (25462) exceeds model's maximum context length (16384).` 4MP 复测是不同输入规格，单独记录，不抹去原图失败；未将缩图配置写入生产。

2B 的关键核验退化：

- `verify_pick_absent`：空桌中不存在可乐罐，却输出 `target_visible=true`、`confidence=0.95`，理由称目标在左下角清晰可见；`target_in_gripper=false` 虽正确，但不能抵消存在性误报。
- `verify_place_absent`：同一目标不存在，仍输出 `target_visible=true`、`target_on_table1=true`、`confidence=0.95`。
- 同轮 9B 及前轮 4B 的这两项预定义字段均通过。这是实际图像核验入口的输出差异，不能只看 HTTP 成功率判断可替换。

大脑看图耗时：4B 有物体／空桌约 **0.773／0.674 秒**，2B 约 **0.565／0.360 秒**。这是小尺寸实时仿真图的端到端取图／描述链路；任务 succeeded 不代表文字描述语义全部正确。没有机器人动作，没有物理抓放验收，没有开启生产的抓放照片核验开关。

## 6. 收尾、证据与使用判断

两个候选测试服务均停止，释放显存；原 9B 服务健康且默认图片路由保留。模型文件、启动脚本、原始回答、失败及资源采样保留。`launch.py --dry-run` 只打印配置，正式启动也不自动修改 Connection 路由。

模型目录内的证据：

- `hf-source.json`、`verified-files.json`：固定版本、文件长度与哈希。
- `trial-spec.json`、`serving-candidate.json`、`launch.py`：实际运行参数。
- 4B：`service_runs/20261020-182226/`、`ab_runs/20261020-182300/`。
- 2B：`service_runs/20261020-183236/`、`ab_runs/20261020-183419/`。
- 各自的 `route_runs/`、4B 的 `route_4mp_runs/`、各自的 `brain_look_runs/`：接口原始结果、任务身份和配置恢复证明。
- 仓库忽略提交目录 `data/small_vlm_20261020/`：总报告、下载／测试脚本及过程日志。

本次没有修改 Connection 生产源码，不重复计入此前的 583＋27 项回归。实际验证为上述 688 次视觉 API 请求、完整文件哈希、脚本语法检查、服务与配置恢复、文档链接检查及 `git diff --check`。

使用判断：两款在本轮达到了约 10GiB 和预热后简单字段三路 ≤5 秒的资源／时延目标，但均未达到“原效果不减少”的要求。4B 还存在本轮上下文配置限制，2B 在核验负例中有高置信度误报；不建议直接全量替换现有 9B，尤其不能将 2B 直接用于本轮失败的抓放图像核验。
